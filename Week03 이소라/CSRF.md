# CSRF (Cross-Site Request Forgery)

## 1. CSRF란?

**CSRF(Cross-Site Request Forgery)**는 사용자가 로그인된 상태라는 점을 악용하여, 공격자가 사용자의 의도와 관계없이 **특정 웹 서비스에 요청을 보내도록 유도하는 공격**이다.

공격자는 피해자의 인증 정보를 직접 알아내지 않아도, 피해자의 브라우저가 이미 가지고 있는 **세션 쿠키 등의 인증 정보가 요청과 함께 전송되는 특성**을 악용할 수 있다.

> CSRF의 핵심은 **사용자가 의도하지 않은 요청을 자신의 권한으로 서버에 전달하도록 만드는 것**이다.

---

## 2. CSRF 발생 원리

일반적인 CSRF 공격 과정은 다음과 같다.

```text
피해자
  ↓
웹 사이트 로그인
  ↓
브라우저에 세션 쿠키 저장
  ↓
공격자가 악성 페이지 제공
  ↓
피해자가 악성 페이지 방문
  ↓
피해자의 브라우저가 대상 서버에 요청 전송
  ↓
브라우저가 인증 쿠키를 함께 전송
  ↓
서버가 정상적인 사용자 요청으로 판단
  ↓
의도하지 않은 작업 수행
```

중요한 점은 공격자가 피해자의 비밀번호를 알아야 하는 것이 아니라는 것이다.

피해자의 브라우저에 이미 유효한 인증 정보가 존재한다면 이를 이용하여 요청을 발생시킬 수 있다.

---

## 3. CSRF 공격 예시

사용자가 웹 사이트에 로그인한 상태에서 계정 설정을 변경하는 요청이 다음과 같다고 가정한다.

```http
POST /account/change-email
```

```text
email=attacker@example.com
```

서버가 요청을 보낸 사용자의 세션만 확인하고, 해당 요청이 실제 사용자의 의도인지 확인하지 않는다면 문제가 발생할 수 있다.

공격자는 피해자가 방문하는 페이지에 자동으로 요청을 발생시키는 요소를 삽입할 수 있다.

```html
<form action="https://example.com/account/change-email" method="POST">
  <input type="hidden" name="email" value="attacker@example.com" />
</form>

<script>
  document.forms[0].submit();
</script>
```

피해자가 이 페이지를 방문하면 브라우저가 대상 서버에 요청을 전송할 수 있다.

---

## 4. CSRF의 조건

CSRF 공격이 성립하기 위해서는 일반적으로 다음과 같은 조건이 필요하다.

| 조건                | 설명                                                                    |
| ------------------- | ----------------------------------------------------------------------- |
| 인증 상태           | 피해자가 대상 서비스에 로그인되어 있어야 함                             |
| 인증 정보 자동 전송 | 브라우저가 요청과 함께 쿠키 등의 인증 정보를 자동으로 전송              |
| 요청 위조 가능      | 공격자가 피해자의 브라우저에서 대상 서버로 요청을 발생시킬 수 있어야 함 |
| 서버 측 검증 부족   | 서버가 요청의 출처나 CSRF 토큰 등을 제대로 검증하지 않음                |

---

## 5. CSRF와 XSS의 차이

| 구분          | XSS                         | CSRF                             |
| ------------- | --------------------------- | -------------------------------- |
| 공격 대상     | 사용자의 브라우저           | 서버의 요청 처리                 |
| 핵심          | 악성 스크립트 실행          | 사용자의 권한으로 요청 위조      |
| 주요 원인     | 입력값을 안전하지 않게 출력 | 요청의 출처/의도를 검증하지 않음 |
| 공격자의 목표 | 브라우저에서 코드 실행      | 사용자가 원하지 않는 작업 수행   |
| 대표적인 방어 | 출력 인코딩, CSP            | CSRF Token, SameSite Cookie      |

### 간단하게 구분하기

```text
XSS
→ "피해자의 브라우저에서 공격자의 코드가 실행"

CSRF
→ "피해자의 브라우저를 이용해 공격자의 요청을 서버에 전달"
```

---

## 6. CSRF Token

CSRF를 방어하는 대표적인 방법은 **CSRF Token**을 사용하는 것이다.

서버가 사용자에게 랜덤한 토큰을 발급하고, 요청을 보낼 때 해당 토큰을 함께 전달하도록 한다.

```text
서버
 ↓
CSRF Token 발급
 ↓
사용자에게 전달
 ↓
정상적인 요청에 Token 포함
 ↓
서버에서 Token 검증
```

예:

```html
<form method="POST">
  <input type="hidden" name="csrf_token" value="random-token-value" />

  <input type="submit" value="변경" />
</form>
```

서버는 요청에 포함된 토큰이 정상적으로 발급한 토큰인지 확인한다.

```text
Token 일치
→ 정상 요청 처리

Token 불일치/없음
→ 요청 거부
```

공격자는 일반적으로 피해자의 CSRF Token 값을 알 수 없기 때문에 위조 요청을 만들기 어려워진다.

---

## 7. SameSite Cookie

쿠키의 `SameSite` 속성을 이용하여 다른 사이트에서 발생한 요청에 쿠키가 전송되는 것을 제한할 수 있다.

```http
Set-Cookie: session=abc123; SameSite=Lax; Secure
```

### SameSite 옵션

| 옵션   | 설명                                               |
| ------ | -------------------------------------------------- |
| Strict | 동일 사이트 요청에서만 쿠키 전송                   |
| Lax    | 일부 cross-site 요청에서는 쿠키 전송을 제한        |
| None   | cross-site 요청에도 쿠키 전송 가능 (`Secure` 필요) |

`SameSite`는 CSRF 방어에 도움을 주지만 애플리케이션의 인증 방식과 사용 사례에 따라 적절한 설정을 선택해야 한다.

---

## 8. Origin / Referer 검증

서버에서 HTTP 요청의 `Origin` 또는 `Referer` 헤더를 확인하여 요청이 허용된 출처에서 발생했는지 검증할 수 있다.

예:

```http
Origin: https://example.com
```

서버가 허용된 출처만 요청을 처리하도록 구성한다.

```text
허용된 Origin
→ 요청 처리

허용되지 않은 Origin
→ 요청 거부
```

다만 헤더 검증만 하나의 방어 수단으로 의존하기보다는 CSRF Token, SameSite Cookie 등의 방어책과 함께 사용하는 것이 일반적이다.

---

## 9. GET 요청을 상태 변경에 사용하지 않기

GET은 일반적으로 데이터를 조회하는 용도로 사용하고, 상태를 변경하는 작업은 POST, PUT, PATCH, DELETE 등의 적절한 HTTP 메서드를 사용한다.

### 좋지 않은 예

```http
GET /account/delete
```

조회용으로 예상되는 GET 요청으로 계정 삭제와 같은 상태 변경 작업을 수행하면 CSRF 공격에 악용될 가능성이 커진다.

### 권장

```http
POST /account/delete
```

그리고 CSRF Token 등의 추가적인 검증을 적용한다.

---

## 10. CSRF 핵심 정리

```text
CSRF
→ 사용자가 로그인된 상태를 악용하여
   사용자의 의도와 관계없이 요청을 보내는 공격

공격 과정
→ 로그인 상태
→ 공격자가 만든 페이지 방문
→ 브라우저가 대상 서버에 요청
→ 인증 정보 자동 전송
→ 서버가 정상 요청으로 처리

주요 방어
→ CSRF Token
→ SameSite Cookie
→ Origin / Referer 검증
→ 상태 변경에 GET 사용하지 않기
```

---

## 11. XSS와 CSRF 관계

XSS와 CSRF는 서로 다른 취약점이지만 함께 발생할 수도 있다.

```text
XSS
→ 공격자가 피해자의 브라우저에서 JavaScript 실행 가능

CSRF
→ 피해자의 브라우저를 이용하여 요청 위조
```

특히 XSS가 존재하는 경우 공격자가 페이지 내부에서 JavaScript를 실행할 수 있기 때문에 **CSRF Token을 탈취하거나 정상적인 요청을 직접 수행하는 등 CSRF 방어를 우회할 가능성**이 있다.

따라서 CSRF Token만 적용하는 것이 아니라 **XSS 자체를 방지하는 것도 중요하다.**
