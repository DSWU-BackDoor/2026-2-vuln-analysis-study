# Command Injection

## 1. Command Injection이란?

OS Command Injection은 웹 애플리케이션에 입력된 사용자 데이터가 운영체제의 명령어에 포함되어 실행될 때 발생할 수 있는 취약점이다.

웹 애플리케이션은 사용자가 입력한 데이터를 이용해 ping, cat 등의 운영체제 명령을 실행하기도 한다. 이때 사용자 입력값에 대한 검증이 제대로 이루어지지 않으면, 공격자가 원래 의도된 명령어 외에 추가적인 OS 명령어를 실행할 수 있다.

예를 들어 다음과 같이 사용자 입력을 명령어에 직접 포함한다고 가정한다.

```
$address = $_GET["address"];
$output = shell_exec("ping -c 3 $address");
```

정상적인 입력으로

127.0.0.1

을 전달하면 다음과 같은 명령이 만들어진다.

ping -c 3 127.0.0.1

하지만 사용자 입력이 별도의 검증 없이 명령어에 들어가기 때문에, 셸의 문법을 이용해 다른 명령어를 추가할 가능성이 생긴다.


결국 Command Injection에서 중요한 것은

사용자 입력 → 명령어 생성 → 셸을 통한 실행

과정이다.

따라서 단순히 특정 공격 문자열을 외우기보다 사용자 입력이 최종적으로 어떤 명령어에 어떤 형태로 들어가는지 확인하는 것이 중요하다.


## 2. Command Injection의 유형

Command Injection은 사용자 입력이 시스템 명령에 전달되는 방식이나 명령 실행 결과의 노출 여부 등에 따라 여러 형태로 구분해서 살펴볼 수 있다.

### Direct Command Injection(직접 명령 인젝션)

사용자가 입력한 값이 OS 명령어의 인자로 직접 들어가는 형태이다.

예를 들어 다음과 같이 사용자 입력이 바로 명령어에 포함되는 경우이다.

```ping [사용자 입력]```

### Indirect Command Injection(간접 명령 인젝션)

사용자 입력이 파일이나 환경 변수 등의 중간 과정을 거쳐 시스템 명령 실행에 영향을 주는 형태이다. 

직접 명령어에 입력값이 들어가지 않더라도, 파일이나 환경 변수 등이 최종적으로 실행되는 명령에 영향을 줄 수 있다.

### Blind Command Injection(블라인드 명령 인젝션)

명령어가 실행되기는 하지만 실행 결과가 HTTP 응답에 직접 나타나지 않는 경우이다.

이 경우에는 명령어 실행 여부를 다른 방법으로 확인해야 한다.

대표적인 방법은 다음과 같다.

- 시간 지연: 명령 실행 시 의도적으로 응답을 지연시켜 확인한다. SLEEP명령(리눅스/유닉스) 또는 루프백 PING을 사용할 수 있다. 속도 저하에는 다양한 원인이 있을 수 있으므로 반복적인 확인이 중요하지만, HTTP 응답이 의도한 만큼 일정하고 반복적으로 지연된다면, 명령 인젝션 공격에 취약한 것으로 생각할 수 있다. 
- 출력 리다이렉션: 명령 실행 결과를 웹루트 또는 그 하위 경로에 파일로 저장한 뒤 해당 파일의 URL을 통해 파일을 조회해 주입된 임의의 명령이 실행됐는지 판단하는 기술이다. 
- Out-of-Band(OOB): 외부 서버와의 통신 등 대역 외 채널을 이용한 기술이다. 취약한 서버를 외부의 서버와 통신하도록 유도하고 기록을 확인함으로써 명령 실행 여부 확인

## 3. Command Injection으로 이어질 수 있는 공격 경로

Command Injection은 특정 입력창에서만 발생하는 것이 아니라, 애플리케이션이 사용자 입력을 처리하는 여러 과정에서 시스템 명령 실행으로 이어질 수 있다.

대표적인 예시는 다음과 같다.

- 사용자가 직접 시스템 명령에 영향을 줄 수 있는 기능
- 임의 파일 업로드 기능
- 서버 측 템플릿 처리 과정
- XML 처리 과정
- 환경 변수나 파일을 이용한 명령 실행

따라서 취약점을 찾을 때는 "어떤 입력값이 시스템 명령 실행에 영향을 주는가?"를 확인하는 것이 중요하다.

## 4. Command Injection의 영향

Command Injection의 영향은 취약한 애플리케이션이 어떤 권한으로 실행되고 있는지에 따라 달라질 수 있다.

낮은 권한으로 실행되는 경우에도 서버 내부의 정보가 노출되거나 파일에 접근할 수 있고, 높은 권한으로 실행되는 경우에는 더 큰 범위의 시스템 작업이 가능해질 수 있다.

따라서 Command Injection은 단순히 명령어 하나를 추가로 실행하는 것에서 끝나는 것이 아니라 서버 자체에 대한 추가적인 공격으로 이어질 가능성이 있는 취약점이다.

## 5. 방지 방법

Command Injection을 방지하기 위해서는 가장 먼저 사용자 입력을 OS 명령어에 직접 연결하는 구조 자체를 피하는 것이 중요하다.

가능하다면 system(), exec()와 같이 셸 명령을 실행하는 방식 대신 해당 기능을 제공하는 라이브러리나 API를 사용하는 것이 좋다.

불가피하게 OS 명령을 실행해야 한다면 다음과 같은 방법을 적용할 수 있다.

사용자 입력에 대한 서버 측 입력 검증
필요한 값만 허용하는 Allowlist 방식
명령어와 사용자 입력을 분리하여 전달
애플리케이션의 최소 권한 실행
운영체제 및 관련 소프트웨어의 지속적인 업데이트

특히 클라이언트 측 입력 제한만으로는 충분하지 않다. 브라우저에서 입력을 제한하더라도 공격자가 직접 HTTP 요청을 만들어 서버에 전달할 수 있기 때문에, 중요한 검증은 반드시 서버 측에서도 이루어져야 한다.

## 6. OWASP Example 1 실습

이번에는 OWASP에서 제공하는 Command Injection 예제 중 Example 1을 직접 실습해 보았다.

출처: [OWASP Community - Command Injection](https://community.owasp.org/attacks/Command_Injection)

해당 예제에서는 UNIX의 cat 명령어를 실행하는 간단한 C 프로그램을 사용한다.

```
#include <stdio.h>
#include <unistd.h>

int main(int argc, char **argv) {
 char cat[] = "cat ";
 char *command;
 size_t commandLength;

 commandLength = strlen(cat) + strlen(argv[1]) + 1;
 command = (char *) malloc(commandLength);
 strncpy(command, cat, commandLength);
 strncat(command, argv[1], (commandLength - strlen(cat)) );

 system(command);
 return (0);
}
```

이 프로그램에서 핵심적으로 확인할 부분은 다음과 같다.

```
char cat[] = "cat ";
...
strcat(command, argv[1]);

system(command);
```

프로그램은 사용자가 전달한 argv[1]을 cat 명령어 뒤에 붙여서 하나의 문자열을 만든다.

예를 들어 ```./catWrapper Story.txt```를 실행하면 프로그램 내부에서는 ```cat Story.txt```이라는 명령어가 발생한다.

따라서 정상적으로 실행하면 Story.txt의 내용이 출력된다.

### 6-1. 실습 환경 구성

Ubuntu 환경에서 해당 예제를 직접 실행하기 위해 C 파일과 테스트용 Story.txt 파일을 준비하였다.

```nano Story.txt```를 통해 테스트할 파일을 생성한 후, 간단한 문구를 작성한 후 저장하였다. 이후 ```gcc commandinjection.c -o catWrapper```를 통해 컴파일을 완료하였다. 

이후 다음 명령어를 실행해 본다. 
```./catWrapper Story.txt```

이 경우 정상적으로 Story.txt에 작성한 내용이 출력되는 것을 확인할 수 있다. 

처음에는 Story.txt의 위치와 현재 작업 디렉터리가 일치하지 않아 파일을 찾지 못하는 오류가 발생하였다.


### 6-2. 취약점 공격(명령어 추가)

정상적으로 프로그램이 동작하는 것을 확인한 뒤, OWASP Example 1에서 제시한 것처럼 파일 이름 뒤에 다른 명령어를 추가하였다.

```./catWrapper "Story.txt; ls"```

이 결과 Story.txt의 내용이 출력된 뒤 ls의 실행 결과도 함께 출력된다. 처리 과정은 아래와 같다. 

```
사용자 입력
    ↓
Story.txt; ls
    ↓
cat + 사용자 입력
    ↓
cat Story.txt; ls
    ↓
system()
    ↓
셸에서 각각의 명령 실행
```

프로그램은 사용자 입력을 문자열에 그대로 연결한 후 system()에 전달한다. system()은 전달받은 문자열을 셸을 통해 해석하기 때문에, 셸이 ;를 명령어를 구분하는 문법으로 인식한다. 따라서 결과적으로 하나의 문자열에 포함되어 있던 명령이 각각 실행된다. 

; 자체가 특별한 공격 문자열이기 때문에 취약한 것이 아니라는 점이 중요하다. 핵심적인 취약점은 사용자 입력을 명령어 문자열에 그대로 연결하여 system()을 통해 실행되게 하는 구조이다. 


### 6-3. 코드 수정

앞선 과정에서 사용자 입력을 명령어 문자열에 직접 연결한 후 system()으로 실행하는 것이 취약점의 원인임을 확인하였다.

기존 코드는 사용자 입력이 포함된 문자열 전체가 셸을 통해 해석될 수 있다.

따라서 단순히 특정 문자를 차단하는 방식보다는, 사용자 입력을 셸 명령어 문자열에 직접 포함시키지 않는 방식으로 코드를 수정하였다.

수정한 코드는 execl()을 사용하여 실행할 프로그램과 인자를 분리해서 전달하도록 하였다.

```
#include <stdio.h>
#include <unistd.h>

int main(int argc, char **argv) {
    if (argc != 2) {
        printf("Usage: %s <filename>\n", argv[0]);
        return 1;
    }

    execl("/bin/cat", "cat", argv[1], (char *)NULL);

    perror("execl");
    return 1;
}
```

기존 코드에서는
```
사용자 입력
    ↓
문자열에 연결
    ↓
완성된 명령어
    ↓
system()
    ↓
셸에서 해석
```
하는 방식이었다면, 

수정한 코드에서는
```
사용자 입력
    ↓
argv[1]
    ↓
/bin/cat의 인자로 전달
```
하는 방식으로 변경하였다.

즉, 실행할 프로그램인 /bin/cat과 사용자가 입력한 파일명을 별도의 인자로 전달하기 때문에 사용자 입력이 셸 명령어로 다시 해석되는 과정을 제거할 수 있다.

수정한 코드를 다시 컴파일한 후 동일한 방식으로 실행하여 정상적으로 파일을 읽을 수 있는지 확인하였다.

이 과정을 통해 Command Injection의 대응 방법을 단순히 이론으로 보는 것이 아니라, 취약한 코드와 이를 개선한 코드의 차이를 직접 비교하며 이해할 수 있었다.



# SQL Injection
## 1. SQL Injection이란?

SQL Injection(SQLi)은 웹 애플리케이션이 사용자 입력을 SQL Query에 안전하게 처리하지 못할 때 발생할 수 있는 취약점이다.

사용자 입력이 단순한 데이터로 처리되지 않고 SQL 문법의 일부로 해석되면서 원래 의도하지 않은 Query가 실행될 수 있다.


## 2. SQL이란?

SQL(Structured Query Language)은 데이터베이스와 데이터를 주고받기 위해 사용하는 언어이다.

웹 서비스에서는 회원 정보, 게시글, 상품 정보, 주문 정보 등 다양한 데이터를 데이터베이스에 저장한다. 웹 애플리케이션은 사용자의 요청에 따라 이러한 SQL Query를 동적으로 만들어 데이터베이스에 전달한다.


## 3. SQL Injection의 주요 유형

SQL Injection은 공격자가 어떤 방식으로 결과를 확인하느냐에 따라 크게 나눌 수 있다.

### In-band SQL Injection

공격을 보내는 통신 경로와 결과를 확인하는 경로가 같은 경우로 대표적으로 다음과 같은 방식이 있다. 

- Error-based SQL Injection: 데이터베이스 오류를 발생시켜 오류 메시지에 포함된 정보를 확인하는 방식
- UNION-based SQL Injection: UNION을 이용하여 기존 Query에 다른 SELECT 문을 결합하는 방식

### Blind SQL Injection

SQL Query는 실행되지만 데이터베이스의 결과가 화면에 직접 표시되지 않는 경우이다. 이 경우에는 서버의 응답 차이 또는 동작 변화를 관찰하여 정보를 추론한다.

- Boolean-based: 조건이 참인지 거짓인지에 따라 응답이 달라지는 것을 이용
- Time-based: 특정 조건에서 의도적으로 응답을 지연시켜 결과를 판단

### Out-of-band SQL Injection

공격을 보내는 경로와 결과를 확인하는 경로가 다른 방식이다.

데이터베이스 서버가 외부로 DNS나 HTTP 요청 등을 보낼 수 있는 환경에서 이러한 통신을 이용하여 공격 결과를 확인할 수 있다.


## 4. SQL Injection의 영향

SQL Injection이 발생하면 애플리케이션의 기능과 데이터베이스 권한에 따라 다양한 피해가 발생할 수 있다.

- 사용자 및 중요 데이터 노출
- 데이터 수정 또는 삭제
- 인증 과정 우회
- 데이터베이스 정보 노출
- 다른 공격으로 이어질 가능성

특히 애플리케이션이 데이터베이스에 높은 권한으로 접근하고 있다면 피해 범위가 커질 수 있다.


## 5. SQL Injection 방어 방법

### Prepared Statement

가장 중요한 방어 방법 중 하나로, SQL Query와 사용자 입력을 하나의 문자열로 직접 합치는 대신 SQL의 구조와 입력값을 분리해서 전달한다.
따라서 사용자가 SQL 문법처럼 보이는 값을 입력하더라도 해당 값을 SQL 명령이 아니라 하나의 데이터 값으로 처리할 수 있다.

### 입력값 검증

서버에서 사용자 입력값을 검증한다. 
다만 입력값에서 특정 문자만 찾아 차단하는 방식만으로 SQL Injection을 완벽하게 막기는 어렵다. 따라서 입력값 검증은 보조적인 방어 수단으로 생각하고, Prepared Statement 등을 통한 구조적인 방어를 우선하는 것이 중요하다.

### 최소 권한

애플리케이션이 데이터베이스에 접속할 때 필요한 권한만 부여해야 한다. SQL Injection이 발생하더라도 데이터베이스 계정의 권한이 제한되어 있다면 피해 범위를 줄일 수 있다.

### 오류 메시지 관리

사용자에게 데이터베이스의 상세 오류 메시지를 그대로 보여주지 않는 것도 중요하다.
따라서 사용자에게는 일반적인 오류 메시지를 보여주고, 상세한 오류 정보는 서버 측 로그에서 관리하는 방식이 적절하다.
