### 2. 소스코드 분석

<img width="600" alt="Image" src="https://github.com/user-attachments/assets/976b09b0-061c-4e46-bae1-64a5f8135ddf" />

이번 워게임의 핵심은 사용자가 입력한 host 값이 어떤 방식으로 명령어에 사용되는지를 확인하는 것이라고 생각했다. 

``` 
host = request.form.get('host') 
cmd = f'ping -c 3 "{host}"' 
```
이 부분을 보면 사용자가 입력한 ```host``` 값을 가져온 뒤, 이를 ```ping``` 명령어 문자열에 그대로 삽입하고 있다. 만약 '0.0.0.0'을 입력하면 최종적으로 ```ping -c 3 "0.0.0.0"```이라는 명령어가 만들어진다. 결론적으로, 사용자의 입력이 명령어의 문자열에 직접 포함된다. 

```
subprocess.check_output(
    ['/bin/sh', '-c', cmd],
    timeout=5
)
```
이어서 코드를 확인해보면, 이 부분에서는 명령어가 어떻게 실행되는지 알 수 있는데, subprocess를 통해 /bin/sh를 실행하고, -c 옵션을 사용하여 cmd에 저장된 문자열을 셸 명령어로 해석하도록 전달한다.

최종적으로 코드가 진행되는 흐름을 요약해보면,
host에 저장된 사용자 입력이 cmd 문자열, 즉 실행할 명령어를 생성하는 과정에 그대로 사용되고, 이후 셸을 통해 실행되는 구조이다. 


문제 페이지의 HTML에서는 Host에 입력할 수 있는 형식이 정해져있었다. 
```pattern="[A-Za-z0-9.]{5,20}" required```

해당 pattern은 브라우저에서 입력값의 형식을 검사하는 정규 표현식이다. [A-Za-z0-9.]은 영문 대소문자, 숫자 및 .을 의미하며, {5,20}은 5자 이상 20자 이하의 입력만 허용한다는 의미이다. 따라서 127.0.0.1은 입력할 수 있지만 ;, ", # 등이 포함된 입력은 브라우저의 입력 형식 검사를 통과하지 못한다.


### 3. 실행 과정

브라우저의 입력창을 이용하여 정상적인 요청을 보냈다. 이 경우 정상적으로 서버의 응답이 반환되는 것을 확인하였다. 

이번 워게임에서의 취약점은 우리가 작성하는 host 번호가 그대로 명령어로 작성되고, 실행된다는 점이라고 생각하였기에, 간단히 검증해보고자 하였다. 

다시 명령어가 어떻게 만들어지는지 살펴보면 
```ping -c 3 "[사용자가 입력하는 host값]"```
의 구조로 명령어가 생성된다. 
사용자의 입력값이 큰따옴표 안에 들어가기 때문에 단순히 입력값 뒤에 명령어를 추가할 경우, host값 자체에 의도하고자 하였던 명령어가 포함된다. 즉 ```;```가 셸의 명령어 구분자로 해석되지 않기 때문에 기존에 열려있는 큰따옴표를 먼저 닫는 형태로 입력을 구성하였다. 

나의 경우 현재 명령을 실행하고 있는 사용자의 계정 및 그룹 정보를 보여주는 명령어인 ```id```를 사용해보기로 했다. 
호스트 번호 뒤에 ```id;#```이라는 명령어를 포함시키고 싶었기 때문에 ```127.0.0.1";id;#```로 입력어를 구성하였다. (처음 시도할 때 ```127.0.0.1;id;#```로 작성하여 어려움이 있었다.)

이 명령어를 그대로 창에 입력할 경우, 조건에 맞지 않는 ```;```와 ```#```이 포함되어있기에 입력하는 형식이 옳지 않아 입력이 불가능했다. 

따라서 터미널에서 HTTP 요청을 직접 보낼 수 있도록 ```curl```을 사용했다. ```curl```은 클라이언트의 검증을 거치치 않고 서버에 직접 요청을 보낼 수 있기 때문에, 지금처럼 형식이 다른 경우에도 문제 없이 보낼 수 있다. 

<img width="400"" alt="Image" src="https://github.com/user-attachments/assets/2a585505-1994-4ae6-b43d-90cc8740b321" />

```curl```: HTTP 요청을 보내는 프로그램
```-X POST```: HTTP 메서드를 POST로 지정
```http://host3.dreamhack.games:18730/ping```: 요청을 전달할 서버의 주소와 ```/ping```엔드포인트
```-d 'host=127.0.0.1'```: POST 요청의 데이터

입력값이 ```127.0.0.1";id;#```일 때 서버에서 생성되는 명령어는 ```ping -c 3 "127.0.0.1";id;#"```이다. 
여기서 첫 번째 "는 기존 ping 명령에서 사용된 큰따옴표를 닫는 역할을 한다. 이후 ;는 셸에서 명령어를 구분하는 역할을 하므로 id가 별도의 명령어로 실행된다. 다시 ;가 등장한 뒤 #이 사용되므로 그 뒤에 남아 있는 마지막 "는 주석 처리되어 명령어 해석에 영향을 주지 않게 된다.

id는 현재 명령을 실행하고 있는 사용자의 UID, GID 및 그룹 정보를 확인할 수 있는 Linux 명령어이다. 따라서 명령어가 실제 서버에서 실행되었는지 확인하는 동시에, 해당 명령이 어떤 사용자 권한으로 실행되고 있는지도 확인할 수 있기 때문에 테스트 명령어로 사용하였다.

<img width="400" alt="Image" src="https://github.com/user-attachments/assets/68c775f0-619c-479a-a180-4ef0a454c51f" />

실제 응답을 보면 ```uid```값과 ```gid```값이 보이는데, 이는 id 명령이 서버에서 실행되었다는 의미이다. 따라서 해당 서버에 Command Injection 취약점이 존재한다는 것을 확인하였다.

### 5. 취약점 발생 원인

이번 문제에서 Command Injection이 발생한 근본적인 원인은 사용자의 입력값을 명령어 문자열에 직접 삽입한 뒤 /bin/sh -c를 통해 셸에서 실행했기 때문이다.


```host = request.form.get('host')```
```cmd = f'ping -c 3 "{host}"'```
```subprocess.check_output(['/bin/sh', '-c', cmd], timeout=5)```

정상적인 입력에서는 host가 단순히 ping의 대상이 되지만, 사용자가 셸에서 특별한 의미를 가지는 문자를 입력하면 최종 명령어의 구조 자체를 변경할 수 있다. 따라서 사용자 입력을 셸 명령어 문자열에 직접 삽입하는 것이 이 문제의 핵심적인 취약점이다.


### 6. 고찰

이번 워게임을 통해 Command Injection이 단순히 특정 문자열을 입력하는 공격이 아니라, 사용자 입력이 프로그램 내부에서 어떻게 처리되고 최종적으로 어떤 명령어로 실행되는지를 분석하는 과정이라는 것을 알게 되었다.

처음에는 ```127.0.0.1;id;#```와 같이 단순히 명령어를 추가하는 방식으로 접근했지만 원하는 결과가 나오지 않았다. 이후 소스코드를 다시 확인하면서 사용자 입력이 ```ping -c 3 "[host]"``` 형태의 큰따옴표 내부에 들어간다는 것을 알게 되었고, 이를 통해 단순히 ;를 추가하는 것이 아니라 입력값이 최종 명령어의 어느 위치에 들어가는지를 먼저 확인해야 한다는 점을 배웠다.

또한 id 명령어를 통해 명령 실행 여부를 확인하면서, 공격 과정에서는 처음부터 중요한 정보를 얻으려고 하기보다 간단한 명령어를 이용해 취약점이 실제로 동작하는지 단계적으로 확인하는 과정이 중요하다는 것도 알게 되었다.

이번 실습에서는 웹 브라우저의 pattern 속성 때문에 원하는 입력값을 직접 입력할 수 없었는데, 이 과정을 통해 클라이언트 측 검증과 서버 측 검증은 별개의 개념이라는 것도 이해할 수 있었다. 브라우저에서 입력을 제한하더라도 서버가 전달받은 값을 안전하게 처리하지 않는다면 다른 방식으로 요청을 전달할 수 있기 때문이다. curl을 사용하면서 웹 브라우저가 실제로는 HTTP 요청을 대신 만들어주는 역할을 한다는 점도 함께 이해할 수 있었다.

이번 실습을 통해 Command Injection의 페이로드를 외우는 것보다, 소스코드를 통해 입력값의 흐름을 분석하고 그 결과에 따라 다음 행동을 결정하는 것이 더 중요하다는 것을 배웠다.
