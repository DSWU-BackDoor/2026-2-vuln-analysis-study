# Access Control (접근 제어) / Broken Access Control

## 1. 개념

**접근 제어(Access Control)** 는 **"누가 무엇을 할 수 있는지"를 강제하는 것**이다.
이게 제대로 지켜지지 않으면 **Broken Access Control(취약한 접근 제어)** 이 되어,
사용자가 **자신의 권한을 넘어선 데이터·기능에 접근**할 수 있게 된다.

- **OWASP 분류**: **A01:2021 - Broken Access Control** (2021년 OWASP Top 10 **1위**)
- **영향**: 타인의 개인정보 열람·수정, 관리자 기능 사용, 비공개 리소스 접근 등
  (실제 영향은 어떤 기능·데이터의 접근 제어가 빠졌는지에 따라 달라진다)

## 2. 인증(Authentication) vs 인가(Authorization)
- **인증**: "너 누구야?" (로그인 — 신원 확인)
- **인가**: "너 이거 해도 돼?" (권한 확인)
- Broken Access Control은 주로 **인가(권한 확인)가 빠지거나 잘못된** 문제다.
  (로그인은 됐는데, 그 사람이 **그 자원에 접근할 권한이 있는지**를 안 따지는 경우)

## 3. 발생 원리

서버가 요청을 처리할 때 **"이 사용자가 이 자원·기능에 접근할 권한이 있는지"를 확인하지 않을 때** 발생한다.

흔한 원인:
- 권한 검사를 **클라이언트(화면)** 에만 의존 (버튼 숨김 등) — 요청은 직접 보낼 수 있음
- **로그인 여부만** 확인하고, **소유권/권한은 확인 안 함**
- 사용자가 준 **id·역할(role) 값을 그대로 신뢰**

## 4. 권한 침해 유형 (한눈에)

| 구분 | 설명 | 예시 |
|------|------|------|
| **수평 권한 상승** | 같은 권한의 **다른 사용자 자원**에 접근 | user1 → user2의 게시글 |
| **수직 권한 상승** | **낮은 권한 → 높은 권한** 기능에 접근 | 일반 user → admin 기능 |
| **IDOR** | **객체 ID 조작**으로 다른 객체 접근 | `/user/1001` → `/user/1002` |

> 관계 정리: **IDOR은 객체에 대한 접근 제어가 제대로 이루어지지 않아 식별자 등을 조작해 다른 객체에 접근할 수 있는 취약점**이고, 수평/수직 권한 상승은 **권한 침해의 유형**이다.
> 예) IDOR로 같은 등급 다른 사용자 자원에 접근하면 → 수평 권한 상승에 해당.

### 4-1. IDOR (Insecure Direct Object Reference)
객체 식별자(id)를 조작해 다른 사용자의 자원에 접근할 수 있는 취약점.
```
GET /mypage?user_id=1001   ← 내 것
GET /mypage?user_id=1002   ← 숫자만 바꾸면 남의 정보 (권한 검사 없음) → 수평 권한 상승
```

### 4-2. 수직 권한 상승 / 기능 수준 접근 제어 실패
낮은 권한 사용자가 **상위 권한 기능을 직접 호출**.
```
일반 사용자
   ↓  POST /admin/deleteUser  (메뉴엔 안 보이지만 직접 요청)
   ↓
서버에서 role(권한) 검사 없음
   ↓
관리자 기능 실행 → 수직 권한 상승
```
→ "관리자 메뉴를 화면에서 숨긴 것"은 접근 제어가 아니다. 서버에서 막아야 한다.

### 4-3. 강제 브라우징 (Forced Browsing)
링크나 메뉴에 노출되지 않은 **기능·리소스의 URL을 직접 요청하여 접근 제어를 우회하는 공격**
```
관리자 메뉴가 일반 사용자 화면에 표시되지 않음
   ↓  /admin/users 직접 요청
   ↓
서버가 권한 검사 없이 응답
   ↓
관리자 기능/자원 접근
```
> **URL을 숨기는 것은 접근 제어가 아니다.** 노출되지 않았다고 보호된 자원은 아니다.

## 5. 취약한 코드 & 실제 요청 예시

### 5-1. 소유권 검사 누락 (IDOR)
```python
# 로그인만 확인하고, 그 글이 "내 글"인지(소유권)는 확인 안 함 → 취약
@app.route('/post/<pid>/delete')
@login_required
def delete(pid):
    db.delete_post(pid)     # 누구의 글이든 삭제 가능
```
→ 다른 사용자의 `pid` 를 넣으면 남의 글도 삭제됨.

### 5-2. 클라이언트가 준 role 을 신뢰
```http
POST /profile HTTP/1.1
Cookie: session=...

{ "role": "admin" }
```
→ 서버가 **요청에 담긴 `role` 값을 그대로 권한 판단에 사용**하면, 일반 사용자가 관리자로 행세할 수 있다.
  (문제는 "role 파라미터가 있다"가 아니라 **서버가 그 값을 신뢰한다**는 점.)

### 5-3. 공격 흐름 요약
```
정상 요청 (user1 로그인)  →  GET /mypage?idx=1001  →  내 정보
       │ idx 값만 1002로 변경
       ▼
GET /mypage?idx=1002  →  서버가 소유권 검사 안 함  →  user2 정보 노출
```

## 6. 방어 방법

1. **보호가 필요한 모든 리소스·기능에 대해 서버 측에서 권한을 검사** ★ — 접근할 때마다 **"이 사용자가 이 자원의 주인/권한자인지"** 확인
2. **기본은 거부(Deny by default)** — 명시적으로 허용된 경우만 접근 허용
3. **소유권 확인** — 자원의 소유자와 요청자가 일치하는지 검사 (IDOR 방지)
4. **화면 숨김에 의존하지 않기** — 버튼·URL을 숨겨도 요청은 직접 올 수 있음 (서버에서 막아야 함)
5. **클라이언트가 준 권한 정보 불신** — role·권한은 **서버 세션/DB** 기준으로 판단
6. **접근 제어 로직 중앙화** — 엔드포인트마다 제각각 말고 공통 미들웨어로 일관 적용

## 7. 핵심 정리

> Broken Access Control은 "로그인은 됐지만 **권한 확인(인가)이 빠진**" 문제다.
> **IDOR(식별자 조작)** 으로 남의 자원에 접근하거나, 숨겨진 관리자 기능을 직접 호출(수직 권한 상승)하는 식으로 악용된다.
> 근본 방어는 **모든 요청마다 서버에서 권한·소유권을 검사**하고, **기본은 거부**로 두는 것이다.
