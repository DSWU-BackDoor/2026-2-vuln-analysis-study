# SSRF (Server-Side Request Forgery)

## 1. 개념

**SSRF(Server-Side Request Forgery, 서버 측 요청 위조)** 는 공격자가 **서버가 요청을 보내는 대상(URL)을
조작**해서, 서버로 하여금 **공격자가 의도한 곳으로 요청을 보내게** 만드는 취약점이다.

핵심은 **요청을 보내는 주체가 "서버"** 라는 점이다. 서버는 보통 **내부망·클라우드 메타데이터 등
외부에서 직접 못 가는 자원에 접근**할 수 있어서, 공격자가 서버를 "대리인"으로 삼아 그런 자원을 노린다.

- **OWASP 분류**: A10:2021 - Server-Side Request Forgery
- **영향**: 내부망 스캔, 내부 서비스 접근, 클라우드 메타데이터 탈취, 방화벽 우회 등
  (실제 영향 범위는 서버가 접근 가능한 네트워크와 응답이 어떻게 반환되는지에 따라 달라진다)

## 2. CSRF와의 차이 (이름이 비슷해 헷갈림)

| 구분 | CSRF | SSRF |
|------|------|------|
| 요청 보내는 주체 | **피해자의 브라우저** | **서버** |
| 노리는 대상 | 그 사이트의 상태 변경 기능 | 서버가 접근 가능한 **내부 자원** |
| 악용하는 것 | 자동 첨부되는 인증 쿠키 | 서버의 **네트워크 위치/권한** |

## 3. 발생 원리

애플리케이션이 **사용자가 준 URL·주소·호스트명**을 받아, **검증 없이 서버가 직접 요청**을 보낼 때 발생한다.

### 취약한 코드 예시 (Python)
```python
# 사용자가 준 url 을 서버가 그대로 가져옴 → 취약
url = request.args.get('url')
resp = requests.get(url)       # 서버가 임의의 주소로 요청
return resp.text
```
- 원래 의도: 외부 이미지 미리보기, 웹훅 전송, URL 썸네일 등
- 악용: `url=http://127.0.0.1:8000/admin`, `url=http://169.254.169.254/...` 처럼
  **내부 주소**를 넣으면 서버가 대신 접근해 응답을 돌려줌

## 4. 공격 흐름

```
[공격자]
   │  악의적인 URL 전달 (url=http://내부주소)
   ▼
[취약한 웹 서버]
   │  서버가 그 URL로 대신 요청
   ▼
[내부망 / 내부 서비스]
   │  응답
   ▼
[웹 서버] ──▶ [공격자]  (Basic이면 응답까지 전달)
```

- **Basic(In-band) SSRF**: 서버가 가져온 응답이 **화면에 그대로 반환**됨 → 내용 직접 확인
  ```
  공격자 → 서버 → 내부 서버 → (응답을 공격자에게 반환)
  ```
- **Blind SSRF**: 응답이 안 보임 → **응답 시간**이나 **외부 수신 서버 로그(요청 도달 여부)** 로 간접 확인
  ```
  공격자 → 서버 → 내부 서버
                 └ 응답 내용은 안 보임 → 외부 서버 로그로 도달 여부만 확인
  ```

## 5. 대표 공격 대상

- **localhost / 내부 IP**: `http://127.0.0.1`, `http://10.0.0.x`, `http://192.168.x.x`
  → 외부에 노출 안 된 관리자 페이지·내부 API 접근
- **클라우드 메타데이터**: `http://169.254.169.254/...`
  → AWS/GCP 등에서 **임시 자격증명·설정 정보** 노출 위험
- **포트 스캔**: 응답 시간·오류 차이로 내부 포트 열림 여부 탐지

### 지원하지 않아야 할 URL scheme
- `file://` → 애플리케이션이 지원할 경우 **로컬 파일 읽기**(예: `/etc/passwd`)로 이어질 수 있음
- `gopher://` → 서버가 지원할 경우 **임의의 TCP 통신**에 악용될 수 있음
- 애플리케이션에 필요한 `http`/`https` 외의 scheme은 **원칙적으로 차단**한다.

## 6. URL 검증 우회 (취약점 분석의 핵심)

"`127.0.0.1` 막으면 끝"이 아니다. **단순 문자열 차단은 쉽게 우회**된다.

### (1) 내부 주소의 다양한 표현
```
127.0.0.1을 직접 차단하더라도 다른 주소 표현이나 localhost 등을
통해 동일한 내부 자원에 접근할 가능성이 있다.

http://localhost
http://[::1]              (IPv6 loopback)
http://2130706433         (127.0.0.1의 정수 표현)
```

### (2) DNS Rebinding (★ 최종 IP 재검증이 필요한 이유)
```
공격자 도메인 입력
   ↓ DNS 조회 → 외부 IP 응답  → 검증 통과
   ↓ (잠시 후) 실제 연결 시점
   ↓ DNS 가 내부 IP 로 바뀜
   ▼
서버가 내부 IP 로 접속 → SSRF 성공
```
검증할 때의 IP와 실제 접속할 때의 IP가 **다를 수 있다.** → **DNS 해석 결과를 검증하고 실제 연결 시점에도 최종 IP를 재검증**해야 함.

### (3) 리다이렉트(Redirect)
```
사용자 입력: https://allowed.example.com   → 검증 통과
   ↓ 서버가 요청
   ↓ 302 Redirect
   ▼
http://127.0.0.1:8080        ← 최종 목적지는 내부 주소
```
처음 URL만 검사하고 **리다이렉트된 최종 목적지를 검사하지 않으면** 내부로 이동할 수 있다.

## 7. 방어 방법

1. **목적지 화이트리스트 + 리다이렉트 대상까지 검증** ★
   - 요청 가능한 도메인/IP를 허용 목록으로 제한하고, **리다이렉트된 최종 목적지도 재검증**
   - (블랙리스트로 내부 IP만 막는 방식은 6절처럼 우회가 많아 불충분)
2. **내부 대역 차단 + 최종 IP 재검증** — `127/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16` 차단
   - DNS 리바인딩 대비: **접속 직전 실제 IP를 다시 확인**, IPv4·IPv6 표현 모두 고려
3. **스킴 제한** — `http`/`https` 외 `file://`, `gopher://` 등 차단
4. **응답 최소 노출** — 가져온 응답 내용을 사용자에게 그대로 반환하지 않아 **정보 유출 범위를 줄이기**
5. **네트워크 분리 / 최소 권한** — 요청 서버가 내부망·메타데이터에 접근 못 하도록 망 분리

## 8. 핵심 정리

> SSRF는 "서버가 보내는 요청의 **목적지**를 공격자가 조종"하는 취약점이다.
> 서버의 네트워크 위치를 악용해 **내부 자원**을 노리며,
> 단순 문자열 차단은 **다른 IP 표현·DNS 리바인딩·리다이렉트**로 우회되므로,
> 근본 방어는 **화이트리스트 + 최종 IP/리다이렉트 재검증 + 망 분리** 다.
