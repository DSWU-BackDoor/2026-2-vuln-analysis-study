# 웹 취약점 분석 스터디 노트 — Access Control

> OWASP Top 10 (2021)에서 **A01: Broken Access Control**로 **1위** 취약점이다.

---

## 1. 개념

**누가(주체) 무엇에(자원) 어떤 행위를 할 수 있는지를 통제하는 것이다.**

- **Authentication(인증)** 은 "너 누구야?"에 해당한다 (신원 확인).
- **Authorization(인가) = Access Control** 은 "너 이거 해도 돼?"에 해당한다 (권한 확인).

> 인증과 인가는 다르다. 로그인에 성공해도(인증 OK) 남의 데이터를 봐선 안 된다(인가 NO).

**Broken Access Control** 은 이 인가 로직이 없거나, 틀렸거나, 우회 가능한 상태를 말한다.

---

## 2. 핵심 원칙

| 원칙                        | 설명                                                                          |
| --------------------------- | ----------------------------------------------------------------------------- |
| 최소 권한 (Least Privilege) | 업무에 필요한 최소한의 권한만 부여한다                                        |
| Deny by Default             | 명시적으로 허용되지 않은 것은 전부 거부한다                                   |
| 서버 측 강제                | 권한 검사는 반드시 서버에서 한다. 클라이언트(JS, 숨긴 버튼)는 신뢰하지 않는다 |
| 책임 분리 (SoD)             | 민감 작업은 한 사람이나 한 권한이 독점하지 못하게 한다                        |

---

## 3. 접근 제어 모델

| 모델                 | 설명                                                                   |
| -------------------- | ---------------------------------------------------------------------- |
| **DAC** (임의적)     | 자원 소유자가 권한을 부여한다 (예: 파일 공유 설정)                     |
| **MAC** (강제적)     | 시스템 정책과 등급(라벨)에 따라 강제한다. 소유자도 못 바꾼다 (군/정부) |
| **RBAC** (역할 기반) | 역할에 권한을 묶고, 사용자에게 역할을 할당한다 (가장 널리 쓰인다)      |
| **ABAC** (속성 기반) | 사용자/자원/환경 속성(부서, 시간, 위치 등)으로 동적으로 판단한다       |

---

## 4. 대표 취약점 유형

### (1) IDOR (Insecure Direct Object Reference)

식별자만 바꿔서 남의 자원에 접근하는 공격이다.

```
GET /account?id=1001   ← 내 계정
GET /account?id=1002   ← 남의 계정인데 그냥 보인다 (소유권 검증 누락)
```

> 가장 흔하고 시험·실무에서 단골로 나온다. 이 자원이 **이 사용자 것이 맞는지** 검사하는 로직이 빠진 것이다.

### (2) 권한 상승 (Privilege Escalation)

- **수직(Vertical)**: 일반 사용자가 관리자 권한을 획득한다.
  - 예: `/admin` 접근 시 URL만 알면 들어가진다.
- **수평(Horizontal)**: 같은 권한 레벨에서 **다른 사용자**의 자원에 접근한다 (IDOR가 대표 케이스다).

### (3) Forced Browsing (강제 탐색)

링크로 노출되지 않은 URL을 직접 입력해 접근한다 (`/admin/config`, `/backup.zip`).
숨겨뒀으니 안전하다는 발상은 보안이 아니다 (Security by Obscurity).

### (4) 파라미터 / 메서드 조작

```
role=user  →  role=admin        (권한 파라미터를 변조한다)
POST는 막아놨는데 PUT/DELETE는 열려 있다 (HTTP 메서드 검증 누락)
```

### (5) JWT / 토큰 조작

- `alg: none`을 허용하거나, 서명키가 약하거나, 서버 측 검증이 누락된다.
- 클레임(`role`, `userId`)을 변조한 뒤 서명을 검증하지 않는다.

### (6) CORS 설정 오류

`Access-Control-Allow-Origin: *`에 인증정보 허용까지 겹치면 교차 출처에서 민감 API를 호출할 수 있다.

---

## 5. 꼭 알아야 할 포인트

- **접근 제어는 모든 요청마다, 서버에서 검사한다.**
  한 번 통과했다고 세션 내내 안전한 것이 아니다.
- **메뉴나 버튼을 숨기는 것은 접근 제어가 아니다.** UI에서 안 보여도 API는 직접 호출할 수 있다.
- 예측 가능한 식별자(순차 ID)는 IDOR에 취약하다. UUID 등 비예측 식별자와 **소유권 검증**을 병행한다.
  (단, UUID 자체는 방어가 아니다. 반드시 서버 측 소유권 확인이 필요하다.)
- 정적 파일, API, 관리자 기능 등 **모든 진입점**을 빠짐없이 커버한다.

---

## 6. 방어 (Mitigation)

1. **Deny by Default** 로 설계한다. 기본 거부, 명시적 허용만 둔다.
2. **서버 측에서 중앙 집중식으로 권한을 검사한다.** 공통 미들웨어나 필터로 일관되게 처리한다.
3. **모든 요청마다 소유권과 권한을 재검증한다.** 특히 객체 참조 시 반드시 확인한다.
4. 민감 식별자는 **세션/토큰에서 가져온 사용자 기준**으로 질의한다.
   ```sql
   -- 나쁨:  SELECT * FROM orders WHERE id = :reqId
   -- 좋음:  SELECT * FROM orders WHERE id = :reqId AND user_id = :sessionUserId
   ```
5. **RBAC/ABAC** 등 명확한 모델을 적용한다.
6. 접근 **실패와 거부를 로깅**하고 이상 징후를 탐지한다 (반복 403 등).
7. **CORS를 최소로 설정**하고 디렉터리 리스팅을 비활성화한다.
8. 레이트 리밋으로 자동화된 IDOR 탐색을 완화한다.
