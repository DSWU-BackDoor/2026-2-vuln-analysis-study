# SSRF (Server-Side Request Forgery)

## 1. SSRF란?

SSRF(Server-Side Request Forgery, 서버 측 요청 위조)는 공격자가 서버에 전달하는 요청을 조작하여, 서버가 의도하지 않은 주소나 리소스에 요청을 보내도록 만드는 취약점이다.

웹 서버는 외부 URL에서 이미지나 파일을 가져오는 등 다른 서버에 요청을 보내기도 한다. 이때 사용자 입력값에 대한 검증이 제대로 이루어지지 않으면 공격자가 요청 대상을 조작할 수 있다.

## 2. SSRF 공격 원리

1. 사용자가 URL이나 요청 대상을 서버에 전달한다.
2. 서버는 입력값을 이용해 외부 또는 내부 서버에 요청을 보낸다.
3. 공격자가 URL을 조작하면 서버가 의도하지 않은 주소에 요청할 수 있다.
4. 이를 통해 내부 서비스에 접근하거나 민감한 정보가 노출될 수 있다.

예를 들어, 이미지 URL을 입력하면 서버가 해당 이미지에 접근해 가져오는 기능이 있다고 가정한다. 공격자가 이미지 주소 대신 내부 서버의 주소를 입력하면, 외부에서는 직접 접근할 수 없는 내부 리소스에 서버를 통해 접근을 시도할 수 있다.

## 3. URL 필터링 우회

SSRF를 방어하기 위해 특정 URL이나 IP 주소를 차단하더라도, 필터링 방식이 불완전하면 우회가 발생할 수 있다.

단순히 문자열에 특정 IP 주소가 포함되어 있는지만 확인해서는 충분하지 않다. URL의 형식, 리다이렉션, DNS 해석 결과 등을 함께 고려해야 한다.

따라서 URL 필터링은 다양한 우회 가능성을 고려하여 구현해야 하며, 입력값 검증만으로는 모든 SSRF 공격을 막기 어렵다는 점을 이해해야 한다.

## 4. SSRF 방어 방법

- **허용 목록(Allowlist):** 서버가 요청할 수 있는 도메인이나 주소를 미리 지정한다.
- **URL 및 IP 검증:** URL 형식과 DNS 해석 결과를 검증하고, 내부 IP 주소나 허용되지 않은 주소로의 요청을 제한한다.
- **리다이렉션 제한:** 허용된 주소에서 다른 주소로 이동하면서 검증을 우회하지 못하도록 리다이렉션을 통제한다.
- **네트워크 접근 제어:** 방화벽 등을 활용해 웹 서버가 내부의 민감한 서비스에 임의로 접근하지 못하도록 제한한다.
- **불필요한 요청 제거:** 외부 리소스를 가져오는 기능을 최소화하고, 필요한 경우에만 서버 측 요청을 허용한다.

# Access Control (접근 제어)

## 1. 접근 제어란?

접근 제어(Access Control)는 사용자나 시스템이 특정 리소스에 접근하거나 작업을 수행할 수 있는지를 결정하는 보안 기술이다.

웹 애플리케이션에서는 사용자마다 접근할 수 있는 페이지와 데이터, 수행할 수 있는 기능이 다르다. 예를 들어 일반 사용자는 자신의 게시글을 확인하고 수정할 수 있지만, 관리자만 다른 사용자의 계정을 관리하거나 게시글을 삭제할 수 있도록 제한할 수 있다.

접근 제어의 주요 목적은 권한이 없는 사용자가 민감한 정보에 접근하거나 허용되지 않은 작업을 수행하지 못하도록 방지하는 것이다. 이를 위해 사용자의 신원과 권한을 확인하고, 요청한 리소스와 작업이 허용되는지 검증해야 한다.

## 2. 인증(Authentication)과 인가(Authorization)의 차이

인증과 인가는 접근 제어를 이해하기 위한 핵심 개념이다.

- **인증(Authentication):** 사용자가 누구인지 확인하는 과정이다. 아이디와 비밀번호, 인증 토큰 등을 통해 사용자의 신원을 확인한다.
- **인가(Authorization):** 인증된 사용자가 특정 리소스에 접근하거나 특정 작업을 수행할 권한이 있는지 확인하는 과정이다.

예를 들어, 사용자가 아이디와 비밀번호를 입력해 로그인하면 인증이 이루어진다. 로그인에 성공했더라도 일반 사용자에게 관리자 페이지의 접근 권한이 없다면 해당 페이지에 접근할 수 없어야 한다. 이때 필요한 것이 인가이다.

따라서 로그인이 정상적으로 이루어졌다는 사실만으로 모든 기능에 접근할 수 있는 것은 아니다. 웹 애플리케이션은 인증과 인가를 각각 올바르게 처리해야 한다.

## 3. 접근 제어 모델

접근 제어 모델은 사용자에게 권한을 부여하고 관리하는 기준에 따라 구분된다.

### 3.1 역할 기반 접근 제어(RBAC)

RBAC(Role-Based Access Control)는 사용자에게 부여된 역할을 기준으로 접근 권한을 결정하는 방식이다.

예를 들어 일반 사용자, 관리자, 운영진이라는 역할을 구분하고 각 역할에 필요한 권한을 부여할 수 있다. 사용자는 자신에게 할당된 역할에 따라 허용된 기능을 이용한다.

- **장점:** 역할별로 권한을 관리하므로 사용자가 많아도 권한 관리가 비교적 쉽다.
- **특징:** 조직이나 서비스에서 사용자 역할이 명확하게 구분될 때 유용하다.

### 3.2 속성 기반 접근 제어(ABAC)

ABAC(Attribute-Based Access Control)는 사용자, 리소스, 요청 환경 등의 속성을 종합적으로 평가하여 접근 권한을 결정하는 방식이다.

예를 들어 사용자의 부서와 직급, 문서의 보안 등급, 접근 시간, 접속 위치 등을 함께 확인하여 접근을 허용하거나 거부할 수 있다.

- **장점:** 다양한 조건을 조합하여 세밀한 접근 제어가 가능하다.
- **특징:** 사용자 역할뿐 아니라 리소스의 특성과 접속 상황까지 고려한다.

### 3.3 관계 기반 접근 제어(ReBAC)

ReBAC(Relationship-Based Access Control)는 사용자와 리소스 사이의 관계를 기준으로 접근 권한을 결정하는 방식이다.

예를 들어 특정 문서의 소유자이거나 해당 문서를 공유받은 사용자만 문서를 열람할 수 있도록 설정할 수 있다. 소셜 네트워크에서 친구 관계에 있는 사용자끼리만 특정 게시물을 볼 수 있도록 제한하는 것도 관련 사례다.

- **장점:** 사용자와 리소스 사이의 관계를 바탕으로 세밀한 권한 관리가 가능하다.
- **특징:** 소유 관계, 공유 관계, 조직 내 관계 등 리소스와 사용자 사이의 연결을 고려한다.

### 3.4 그 외 접근 제어 모델

- **임의 접근 제어(DAC):** 리소스 소유자가 다른 사용자에게 접근 권한을 부여하거나 취소할 수 있는 방식이다.
- **필수 접근 제어(MAC):** 시스템에서 정한 보안 정책과 보안 등급에 따라 접근을 제한하는 방식이다.
- **룰 기반 접근 제어(RuBAC):** 사전에 정의된 규칙이나 조건에 따라 접근을 허용하거나 거부하는 방식이다.

각 모델은 권한을 판단하는 기준이 다르며, 실제 시스템에서는 여러 접근 제어 방식을 함께 사용할 수도 있다.

## 4. 접근 제어의 유형

웹 애플리케이션의 접근 제어 취약점은 권한을 확인하는 기준에 따라 다음과 같이 구분할 수 있다.

### 4.1 수직적 접근 제어(Vertical Access Control)

수직적 접근 제어는 서로 다른 권한 수준을 가진 사용자 사이의 접근을 제한하는 방식이다.

예를 들어 일반 사용자는 게시글을 조회할 수 있지만, 관리자만 게시글을 삭제하거나 다른 사용자의 계정을 관리할 수 있도록 설정한다.

공격자가 일반 사용자 계정으로 관리자 전용 기능에 접근할 수 있다면 수직적 접근 제어가 제대로 구현되지 않은 것이다.

### 4.2 수평적 접근 제어(Horizontal Access Control)

수평적 접근 제어는 비슷한 권한 수준에 있는 사용자라도 서로의 데이터에 무단으로 접근하지 못하도록 제한하는 방식이다.

예를 들어 사용자 A와 사용자 B가 모두 일반 사용자이더라도, A는 자신의 주문 내역만 조회할 수 있어야 한다. A가 요청에 포함된 주문 번호를 B의 주문 번호로 변경했을 때 B의 정보까지 확인할 수 있다면 수평적 접근 제어 취약점이 존재할 수 있다.

### 4.3 컨텍스트 기반 접근 제어(Context-Based Access Control)

컨텍스트 기반 접근 제어는 사용자의 신원과 역할뿐 아니라 접근 시간, 접속 위치, 네트워크 상태, 인증 수준 등의 상황 정보를 고려하여 접근 권한을 결정하는 방식이다.

예를 들어 평소와 다른 환경에서 접속하거나 보안이 확인되지 않은 네트워크를 이용하는 경우 추가 인증을 요구할 수 있다.

이 방식은 접근 당시의 상황에 따라 권한을 세밀하게 제한하는 데 활용된다.

## 5. 접근 제어 미흡의 주요 취약점

### 5.1 IDOR (Insecure Direct Object Reference)

IDOR은 사용자가 전달한 객체 식별자를 이용해 리소스에 접근할 때, 서버가 해당 리소스에 대한 권한을 제대로 확인하지 않아 발생하는 취약점이다.

예를 들어 URL에 `user_id=1001`과 같은 값이 포함되어 있고, 서버가 로그인 여부만 확인한 채 데이터를 반환한다고 가정한다. 사용자가 이 값을 `user_id=1002`로 변경했을 때 다른 사용자의 정보가 반환된다면 IDOR 취약점이 발생한 것이다.

핵심 원인은 식별자 자체가 아니라, **요청한 사용자가 해당 리소스에 접근할 권한이 있는지 서버가 확인하지 않는 것**이다.

### 5.2 파라미터 변조(Parameter Tampering)

파라미터 변조는 사용자가 전달하는 요청값을 임의로 변경하여 의도하지 않은 기능을 실행하거나 제한된 데이터에 접근하려는 행위다.

예를 들어 요청에 포함된 사용자 ID, 주문 번호, 역할 정보, 가격 등의 값을 변경할 수 있다. 서버가 클라이언트에서 전달한 값을 신뢰하고 별도의 검증 없이 처리하면 권한 상승이나 데이터 조작 등의 문제가 발생할 수 있다.

따라서 중요한 권한 정보와 데이터의 유효성은 서버에서 검증해야 한다.

### 5.3 강제 브라우징(Forced Browsing)

강제 브라우징은 웹사이트에서 링크나 메뉴를 통해 노출되지 않은 URL을 직접 입력하거나 추측하여 접근을 시도하는 방식이다.

예를 들어 일반 사용자에게 관리자 페이지 링크가 보이지 않더라도, 사용자가 관리자 페이지의 주소를 직접 입력할 수는 있다. 서버가 접근 권한을 확인하지 않는다면 일반 사용자가 관리자 기능을 이용할 수 있다.

따라서 메뉴를 숨기거나 URL을 공개하지 않는 것만으로는 접근 제어가 충분하지 않으며, 서버에서 요청마다 권한을 확인해야 한다.

## 6. 접근 제어 방어 방법

- **서버 측 권한 검증:** 페이지를 표시하는 단계뿐 아니라 데이터를 조회하거나 수정·삭제하는 모든 요청에서 사용자의 권한을 확인한다.
- **최소 권한 원칙:** 사용자에게 업무나 서비스 이용에 필요한 최소한의 권한만 부여한다.
- **리소스 소유권 확인:** 요청한 사용자가 해당 게시글, 파일, 주문 내역 등의 소유자이거나 접근 권한을 부여받은 사용자인지 확인한다.
- **클라이언트 입력값 신뢰 금지:** 사용자 ID, 역할, 권한, 가격 등의 값을 클라이언트에서 전달받더라도 그대로 신뢰하지 않고 서버에서 검증한다.
- **직접 URL 접근 제한:** 메뉴에 표시되는지 여부와 관계없이 보호된 URL에 대한 접근 권한을 서버에서 확인한다.
- **접근 제어 정책 일관성 유지:** API와 웹 페이지 등 모든 접근 경로에 동일한 권한 정책을 적용한다.
- **로그 및 감사 관리:** 비정상적인 접근 시도와 권한 변경 기록을 확인하고, 반복적인 접근 실패나 의심스러운 요청을 탐지한다.
- **정기적인 권한 검토:** 불필요하거나 오래된 권한을 제거하고, 사용자 역할과 리소스 접근 권한이 적절하게 설정되어 있는지 점검한다.git add "Week04/김지우/wargame.
