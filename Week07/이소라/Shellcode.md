# 시스템 취약점 분석 스터디 노트 — Shellcode (셸코드)

> 셸코드는 그 자체로 취약점이 아니라, Buffer Overflow·OOB 같은 **메모리 손상 취약점으로 실행 흐름을 탈취한 뒤 실제로 실행시키는 "페이로드(payload)"** 다. "흐름을 뺏는 법(취약점)"과 "뺏은 뒤 뭘 할지(셸코드)"는 분리해서 이해해야 한다.

---

## 1. 개념

**실행 흐름을 장악한 공격자가 CPU에게 직접 실행시키려고 넣는, 아주 짧은 기계어(머신코드) 조각이다.**

- 이름이 **shell**code인 이유는, 고전적으로 그 목적이 **셸(`/bin/sh`)을 띄우는 것**이었기 때문이다. 셸을 얻으면 공격자가 그 권한으로 명령을 자유롭게 실행할 수 있어서 가장 강력한 결과였다.
- 지금은 셸을 띄우는 것 말고도 **파일 읽기, 포트 열기(바인드 셸), 역접속(리버스 셸), 권한 상승** 등 다양한 동작을 하지만, 관습적으로 전부 "셸코드"라고 부른다.

> BOF/OOB 노트와의 연결: 그 노트들의 "쉘코드 주입(Shellcode Injection)"에서 **RET를 버퍼 주소로 돌린다**고 한 그 버퍼 안에 들어가는 내용물이 바로 이 셸코드다.

셸코드는 보통 C가 아니라 **어셈블리로 작성**된다. 짧아야 하고(버퍼에 들어가야 함), 외부 라이브러리나 로더 없이 **혼자 동작**해야 하며, 바이트 하나하나를 통제해야 하기 때문이다.

---

## 2. 핵심 구조 — 어셈블리에서 바이트열까지

셸코드는 결국 **메모리에 올라가는 바이트 배열**이다. 작성 → 실행까지 3단계로 본다.

```
어셈블리 소스  →  어셈블(assemble)  →  기계어 바이트열  →  취약점으로 주입 후 실행
 (사람이 읽음)                        "\x48\x31\xf6..."    (CPU가 읽음)
```

| 단계     | 내용                                 | 예               |
| -------- | ------------------------------------ | ---------------- |
| 어셈블리 | CPU 명령어를 사람이 읽는 형태로 작성 | `xor rsi, rsi`   |
| 기계어   | 어셈블러가 바이트로 변환             | `48 31 f6`       |
| 바이트열 | 익스플로잇에 넣는 문자열 형태        | `"\x48\x31\xf6"` |

> 핵심은 "**셸코드 = 데이터처럼 생긴 코드**"라는 점이다. 취약점으로 이 바이트열을 메모리에 올리고, 실행 흐름(RET, 함수 포인터 등)을 그 바이트열의 시작 주소로 돌리면, CPU가 데이터를 **명령어로 해석해서 실행**한다. NX/DEP는 바로 이 "데이터 영역을 명령어로 실행"하는 것을 막는 보호 기법이다 (5장).

---

## 3. 작동 원리 — 시스템 콜(syscall)

셸코드가 `printf` 같은 **라이브러리 함수를 못 쓰는 경우가 많다** (주소를 모르거나, 로더 도움을 못 받으므로). 그래서 커널에게 직접 일을 시키는 **시스템 콜(syscall)** 을 쓴다.

리눅스 x86-64에서 시스템 콜은 이렇게 호출한다.

| 레지스터       | 역할                                                            |
| -------------- | --------------------------------------------------------------- |
| `rax`          | **시스템 콜 번호** (예: `execve`는 59, `read`는 0, `write`는 1) |
| `rdi`          | 첫 번째 인자                                                    |
| `rsi`          | 두 번째 인자                                                    |
| `rdx`          | 세 번째 인자                                                    |
| `syscall` 명령 | 커널로 진입해 실제 실행                                         |

### 대표 예시 — `execve("/bin/sh", NULL, NULL)`

셸을 띄우는 가장 고전적인 셸코드는 결국 아래 C 한 줄과 같다.

```c
execve("/bin/sh", NULL, NULL);   // 현재 프로세스를 /bin/sh로 교체 → 셸 획득
```

이걸 어셈블리로 풀면 (교과서에 나오는 대표 형태):

```asm
; execve("/bin/sh", 0, 0)  — 리눅스 x86-64
xor  rsi, rsi          ; rsi = 0  (argv = NULL)
xor  rdx, rdx          ; rdx = 0  (envp = NULL)
mov  rdi, 0x68732f6e69622f   ; "/bin/sh" 문자열을 거꾸로 담아 스택에 올림
push rsi               ; 문자열 끝 널 바이트
push rdi
push rsp
pop  rdi               ; rdi = "/bin/sh" 주소
mov  rax, 59           ; execve의 시스템 콜 번호
syscall                ; 커널 진입 → 셸 실행
```

> 흐름 요약: ① 인자(`rdi/rsi/rdx`)를 세팅하고 → ② `rax`에 콜 번호를 넣고 → ③ `syscall`로 커널에 넘긴다. **인자 세팅 + 콜 번호 + syscall**, 이 3박자가 모든 셸코드의 뼈대다. (위 예시는 개념 이해용이며, 실제 바이트는 어셈블 방식·정렬에 따라 달라진다.)

## 4. 셸코드의 제약과 기법

취약점을 통과해 **온전히 메모리에 올라가고, 어디에 놓여도 동작**해야 하므로 여러 제약을 넘겨야 한다. 시험 단골 포인트다.

### (1) Null-byte 문제 (`\x00`)

가장 중요한 제약이다. `strcpy`, `gets`, `scanf("%s")` 같은 **문자열 함수는 널 바이트(`0x00`)를 "문자열 끝"으로 보고 거기서 복사를 멈춘다.** 셸코드 중간에 `\x00`이 있으면 그 앞까지만 들어가고 **뒤가 잘린다.**

그래서 셸코드는 **널 바이트가 없게(null-free)** 작성한다. 대표적인 회피 기법:

| 문제 코드     | 바이트                         | 회피 코드      | 바이트     | 효과                                |
| ------------- | ------------------------------ | -------------- | ---------- | ----------------------------------- |
| `mov rax, 0`  | `...00 00 00 00`               | `xor rax, rax` | `48 31 c0` | 레지스터를 0으로 만들 때 `xor` 사용 |
| `mov rax, 59` | 작은 값이라 상위 바이트가 `00` | `mov al, 59`   | `b0 3b`    | 하위 8비트 레지스터(`al`)만 사용    |

> 핵심 문장: "**셸코드에 널 바이트가 있으면 문자열 함수에서 잘리므로, `xor`·하위 레지스터 등으로 널 바이트를 없앤다.**" 입력 통로에 따라 금지 문자가 더 있을 수도 있다 (공백, 개행, 영숫자만 허용 등 → bad char).

### (2) 위치 독립성 (Position-Independent)

셸코드가 메모리 **어느 주소에 놓일지 미리 알 수 없다** (ASLR 때문에도). 그래서 절대 주소를 하드코딩하지 않고, 필요한 문자열(`/bin/sh`)도 **스택에 직접 쌓아서** 상대적으로 참조한다 (3장 예시에서 `push`로 올린 이유).

### (3) NOP Sled (NOP 썰매)

RET를 돌릴 **정확한 셸코드 시작 주소를 모를 때**, 앞에 아무 일도 안 하는 명령어 `NOP`(`0x90`)를 길게 깐다. 대략적인 주소로만 점프해도 NOP 구간에 떨어지면 CPU가 **아래로 주르륵 미끄러져 내려와** 셸코드 시작에 도달한다.

```
[ 0x90 0x90 0x90 ... 0x90 ][ 셸코드 ]
   ↑ NOP sled (여기 아무 데나 떨어져도 OK)   ↑ 실제 코드
```

> BOF 노트의 "쉘코드 주입" 항목에서 나온 그 NOP Sled다. 주소 추측의 오차 범위를 넓혀 명중률을 높이는 장치다.

### (4) 스테이징 / Egg-hunter (개념 소개)

넣을 수 있는 공간이 **셸코드보다 작을 때** 쓰는 2단계 전략이다.

- **1단계(스테이저):** 아주 작은 코드만 먼저 넣는다.
- **2단계:** 그 작은 코드가 진짜 큰 셸코드를 **메모리에서 찾아가거나, 추가로 받아와** 실행한다.
- **Egg-hunter:** 큰 셸코드 앞에 독특한 표식("egg", 예: `w00tw00t`)을 붙여두고, 작은 코드가 메모리를 뒤져 그 표식을 **찾아(hunt)** 점프하는 방식이다.

> 깊게 외울 필요는 없고, "**공간이 부족하면 작은 코드로 큰 코드를 찾아 실행하는 2단계 기법이 있다**" 정도로 개념만 알아두면 된다.

## 5. 보호 기법과의 관계

셸코드 **주입·실행**을 막거나 무력화하는 보호 기법들이다. BOF/OOB 노트의 보호 기법 표와 이어서 본다.

| 보호 기법        | 셸코드에 대한 효과                                                                                                                 | 우회 / 대응                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **NX / DEP**     | 스택·힙 같은 **데이터 영역을 실행 불가**로 만든다. 거기 올린 셸코드는 **실행 자체가 안 된다.** 셸코드 주입을 직접 막는 핵심 방어다 | 데이터를 실행하지 않는 **ROP / ret2libc**로 전환 (아래)                              |
| **ASLR / PIE**   | 주소를 무작위화해 **셸코드 시작 주소를 못 맞추게** 한다                                                                            | NOP Sled로 오차 흡수, 또는 주소 유출(Leak)                                           |
| **Stack Canary** | 셸코드 자체를 막진 않지만, 셸코드로 가는 통로인 **BOF의 RET 덮어쓰기를 탐지**한다                                                  | 카나리 값 유출                                                                       |
| **seccomp**      | 프로세스가 쓸 수 있는 **시스템 콜을 화이트리스트로 제한**한다. `execve`가 막혀 있으면 셸을 띄우는 셸코드가 통하지 않는다           | 허용된 콜(`open`/`read`/`write`)만으로 **플래그를 읽어 출력**하는 셸코드(ORW)로 전환 |

### NX를 만나면 → ROP / ret2libc로

**NX/DEP가 켜지면 "데이터를 명령어로 실행"하는 전통적 셸코드 주입은 실패한다.** 그래서 공격의 무게 중심이 옮겨간다.

- **ret2libc:** 셸코드를 넣는 대신, 이미 메모리에 **실행 가능 상태로 존재하는** 라이브러리 함수(예: `system("/bin/sh")`)로 RET를 돌린다.
- **ROP (Return-Oriented Programming):** 기존 코드의 `ret`으로 끝나는 조각(가젯)을 엮어, 원하는 레지스터를 세팅하고 `syscall`/함수 호출을 **직접 넣지 않고 "빌려서"** 수행한다.

> 흐름으로 외우기: **셸코드 주입 → (NX 등장) → ret2libc → (더 일반화) → ROP.** 즉 "내 코드를 넣어 실행"이 막히니 "남의 코드를 이어 붙여 실행"으로 넘어간 것이다. seccomp처럼 `execve`까지 막히면 ROP/셸코드 모두 **ORW(open-read-write)로 플래그만 읽는 방향**으로 바뀐다.

## 6. 꼭 알아야 할 포인트

- **셸코드는 취약점이 아니라 "페이로드"다.** 흐름 탈취(BOF/OOB)는 "수단", 셸코드는 "목적(실행할 코드)"이다. 둘을 분리해서 말할 수 있어야 한다.
- **셸코드의 뼈대 = 인자 세팅(`rdi/rsi/rdx`) + 콜 번호(`rax`) + `syscall`.** `execve("/bin/sh", 0, 0)`이 가장 대표적이다 (x86-64 `execve` 번호 **59**).
- **왜 널 바이트를 없애나?** → 문자열 함수가 `\x00`에서 복사를 멈춰 셸코드가 **잘리기** 때문이다. `xor`로 0을 만들고, 하위 레지스터(`al`)를 써서 null-free로 만든다.
- **NOP Sled는 왜 쓰나?** → 셸코드 **시작 주소를 정확히 몰라도** 명중시키려고. 대략 점프 후 미끄러져 내려오게 한다.
- **NX/DEP를 만나면?** → 데이터 실행이 막히므로 셸코드 주입 대신 **ret2libc / ROP**로 간다. (BOF 노트와 동일한 결론)

### 비교 — 셸코드 주입 vs ROP

| 구분             | 셸코드 주입 (Shellcode Injection) | ROP (Return-Oriented Programming)        |
| ---------------- | --------------------------------- | ---------------------------------------- |
| 실행하는 코드    | 공격자가 **새로 넣은** 기계어     | 프로그램에 **이미 있는** 코드 조각(가젯) |
| 데이터 실행 여부 | 데이터 영역을 실행해야 함         | 실행 가능한 코드만 사용                  |
| **NX/DEP**       | **막힌다** (실행 불가)            | 우회 가능                                |
| 난이도 / 공간    | 비교적 단순, 공간 필요            | 복잡, 가젯 탐색 필요                     |

### 보호 기법 요약 (셸코드 관점)

| 보호 기법        | 셸코드를 막나? | 한 줄 요약                                 |
| ---------------- | -------------- | ------------------------------------------ |
| **NX / DEP**     | ✅ 직접 막음   | 데이터 영역 실행 금지 → 주입 셸코드 무력화 |
| **ASLR / PIE**   | △ 명중률 저하  | 주소 무작위화 → NOP Sled·Leak로 대응       |
| **Stack Canary** | △ 통로 차단    | RET 덮어쓰기 탐지(간접 방어)               |
| **seccomp**      | ✅ 동작 제한   | `execve` 등 시스템 콜 차단 → ORW로 우회    |

## 7. 방어 (Mitigation)

셸코드는 "주입"과 "실행" 두 단계를 거치므로, 각 단계를 끊는 것이 방어의 핵심이다.

1. **NX/DEP를 켠다.** 스택·힙을 실행 불가로 만들어 **주입된 셸코드의 실행 자체를 막는다.** (`-Wl,-z,noexecstack`) 셸코드 방어의 1순위다.
2. **애초에 흐름 탈취를 막는다.** 셸코드가 실행되려면 먼저 실행 흐름이 넘어가야 하므로, **BOF/OOB 자체를 막는 것**(경계 검사, 위험 함수 제거, Stack Canary)이 근본 방어다.
3. **ASLR / PIE를 유지한다.** 주소를 무작위화해 셸코드·가젯의 위치를 못 맞추게 한다 (`randomize_va_space = 2`).
4. **seccomp로 시스템 콜을 제한한다.** 프로세스에 꼭 필요한 콜만 화이트리스트로 허용하면, `execve` 기반 셸 획득을 원천 차단할 수 있다 (`seccomp-bpf`).
5. **CFI / Shadow Stack을 적용한다.** 실행 흐름이 정상 경로를 벗어나는 것(ROP 포함)을 탐지·차단한다 (Intel CET 등).
6. **입력 검증과 런타임 검사를 병행한다.** 입력 길이·형식을 검증하고, AddressSanitizer·퍼징으로 셸코드가 들어올 통로(메모리 손상)를 개발 단계에서 제거한다.
7. **최소 권한으로 실행한다.** 셸코드가 끝내 실행돼도 피해가 번지지 않도록, 서비스를 낮은 권한·샌드박스·컨테이너로 격리한다.

> 한 줄 정리: **"통로(BOF/OOB)를 막고(2·6), 실행을 막고(1·5), 띄워도 못 쓰게(4·7) 한다."** 겹겹이 쌓는 Defense in Depth가 핵심이다.
