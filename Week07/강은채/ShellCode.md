# Shellcode

## 1. 개념

### 1-1. 셸코드란?

- **셸코드(Shellcode)**는 메모리 손상 취약점(버퍼 오버플로우 등)을 통해 제어 흐름을 탈취한 공격자가 그 직후 실행시키려는 **작은 기계어 조각**이다. 이름은 과거에 셸(`/bin/sh`)을 띄우던 데서 유래했으나, 실제로는 공격자가 실행하려는 임의 코드인 **페이로드**를 통칭한다.
- **분류**: 셸코드는 취약점(CWE) 자체가 아니라, 취약점을 이용한 **익스플로잇의 페이로드(실행 단계)** 를 구성하는 요소이다.
    - 함께 다뤄지는 취약점 계열: CWE-787(Out-of-bounds Write), CWE-121(Stack-based Buffer Overflow), CWE-94(Code Injection) 등
- **형태**: CPU가 바로 실행할 수 있는 바이트 시퀀스. 보통 `\x90\x48\x31\xc0...` 같은 hex 바이트로 표현한다.
- **학습 의의**: 취약점 자체(메모리 손상)와, 그 취약점으로 무엇을 하는가(페이로드)를 분리해서 이해하는 것이 익스플로잇 분석의 핵심이다. 앞 단계(제어 흐름 탈취)가 더 핵심 학습 포인트인 경우가 많다.

### 1-2. 전체 공격 체인에서의 위치

셸코드는 단독으로 동작하지 않고, 선행 취약점이 **제어 흐름을 넘겨줘야** 실행된다.

```
취약점(버그) → 제어 흐름 탈취(RIP/EIP 장악) → 페이로드(shellcode) 실행
    │                    │                           │
 BOF/OOB 등        RET·함수포인터 덮기          execve("/bin/sh") 등
```

→ 즉 셸코드는 공격 체인의 마지막 **실행** 단계에 해당한다.

## 2. 배경 지식

### 2-1. 메모리 영역과 실행 권한

셸코드 공격의 성립 여부는 그 메모리에서 **코드를 실행할 수 있는가**에 달려 있다.

| 영역 | 용도 | 일반적인 권한 |
| --- | --- | --- |
| 코드(.text) | 실행할 명령어 | 읽기 + **실행** (쓰기 불가) |
| 데이터(.data/.bss) | 전역 변수 | 읽기 + 쓰기 |
| 힙(Heap) | 동적 할당 | 읽기 + 쓰기 |
| 스택(Stack) | 지역 변수, 함수 프레임 | 읽기 + 쓰기 |
- 전통적 셸코드 공격은 **쓰기 가능한 스택/힙에 코드를 넣고 그곳으로 점프**한다.
- 그러나 현대 OS는 NX/DEP로 데이터 영역의 실행을 금지한다.

### 2-2. 레지스터와 호출 규약

| 레지스터 (x86-64) | 역할 |
| --- | --- |
| `RIP` | 다음에 실행할 명령어 주소. 직접 수정 불가, `call`/`ret`/`jmp`로만 변경 |
| `RSP` | 스택 포인터 |
| `RAX` | 함수 반환값 / **syscall 번호** |
| `RDI, RSI, RDX, RCX, R8, R9` | System V ABI 함수 인자 1~6번 (순서대로) |

> 공격의 최종 목표는 결국 **`RIP`를 공격자가 원하는 값으로 만드는 것**이고,
셸코드가 실행되면 **syscall을 세팅하기 위해** `RAX`와 인자 레지스터를 조작한다.
> 

### 2-3. 시스템 콜

셸코드가 실제로 하는 일은 커널에 **시스템 콜(syscall)**을 요청하는 것이다(파일 열기, 프로세스 실행, 네트워크 연결 등). 셸을 띄우려면 `execve("/bin/sh", NULL, NULL)`를 호출한다.

| 구분 | x86 (32bit) | x86-64 (64bit) |
| --- | --- | --- |
| 호출 명령 | `int 0x80` | `syscall` |
| syscall 번호 레지스터 | `EAX` | `RAX` |
| `execve` 번호 | 11 (`0x0b`) | 59 (`0x3b`) |
| 인자 전달 | `EBX, ECX, EDX ...` | `RDI, RSI, RDX ...` |

## 3. 셸코드가 만족해야 하는 제약

실제 익스플로잇에서 셸코드는 아무 바이트나 되는 게 아니라, **입력 경로의 제약**을 통과해야 한다.

| 제약 | 설명 | 대응(변형) 기법 |
| --- | --- | --- |
| **길이 제한** | 버퍼 크기 안에 들어가야 함 | 코드 최소화, 스테이저(stager) 사용 |
| **금지 바이트(bad char)** | `strcpy`는 `\x00`에서 끊김, `scanf`/`gets`는 `\x0a`(개행)·공백 등에서 끊길 수 있음 | NULL-free 작성, `xor`로 0 생성 |
| **위치 독립성(PIC)** | 로드될 주소를 모르므로 절대 주소에 의존 불가 | 문자열을 스택에 push, 상대주소 사용 |
| **정렬(alignment)** | x86-64는 특정 호출 전 스택 16바이트 정렬을 요구하는 경우가 있음 | 스택 패딩 조정 |

→ 이 때문에 **NULL-free 셸코드**, **alphanumeric 셸코드**(출력 가능한 문자만 사용), **polymorphic/encoded 셸코드**(시그니처 탐지 회피) 같은 변형 기법이 연구 주제가 된다.

## 4. 셸코드 구조와 동작 원리

> 아래는 리눅스 x86-64에서 셸을 띄우는 **고전적인 교육용 셸코드**를 "작성 → 바이트 추출 → 분석"하는 과정이다.
취약점 분석 스터디의 목적은 **주어진 바이트가 무슨 일을 하는지 읽어내는 것**이므로, 분석 흐름에 비중을 둔다.
> 

### 4-1. `execve("/bin/sh")` 셸코드 분석

```nasm
; execve("/bin/sh", NULL, NULL)  - x86-64, syscall 번호 59
_start:
    xor  rsi, rsi                 ; rsi = 0  (argv = NULL)
    push rsi                      ; 스택에 NULL 종료자 push
    mov  rdi, 0x68732f6e69622f2f  ; "//bin/sh" (리틀엔디안, 8바이트 맞추려 '/' 하나 추가)
    push rdi
    push rsp
    pop  rdi                      ; rdi = 스택에 올린 "//bin/sh" 주소
    xor  rdx, rdx                 ; rdx = 0  (envp = NULL)
    push 59
    pop  rax                      ; rax = 59 (execve)
    syscall                       ; 커널 요청 → 셸 실행
```

**왜 이렇게 짜는가 (분석 포인트)**

- `xor reg, reg`로 0을 만드는 이유 → `mov reg, 0`은 기계어에 `\x00`을 포함해 **금지 바이트**가 되기 때문.
- `"/bin/sh"`를 데이터 영역이 아니라 **스택에 직접 push**하는 이유 → 로드 주소를 몰라도 되는 **위치 독립성(PIC)** 확보.
- `"//bin/sh"`로 `/`를 하나 더 넣은 이유 → 8바이트(레지스터 크기)에 맞추기 위함. 경로상 `//bin/sh` == `/bin/sh`.
- `RAX`에 syscall 번호(59), `RDI/RSI/RDX`에 인자를 세팅하고 `syscall`.

### 4-2. 어셈블 → 바이트 추출

```bash
# nasm으로 어셈블 후 .text 바이트만 추출
nasm -f elf64 sh.asm -o sh.o
objcopy -O binary -j .text sh.o sh.bin
xxd -i sh.bin        # C 배열 형태로 바이트 확인
```

추출되는 바이트(널 바이트 없음!!)

```
48 31 f6                   xor  rsi, rsi
56                         push rsi
48 bf 2f 2f 62 69 6e 2f 73 68   movabs rdi, 0x68732f6e69622f2f
57                         push rdi
54                         push rsp
5f                         pop  rdi
48 31 d2                   xor  rdx, rdx
6a 3b                      push 0x3b
58                         pop  rax
0f 05                      syscall
```

### 4-3. 테스트 하네스로 실행 & 분석

취약점 없이도 셸코드 동작만 확인하려면 바이트를 **실행 가능한 메모리에 올려 호출**하는 작은 로더를 쓴다. (OOB 노트에서 ASan으로 탐지 로그를 확인했던 것과 같은, 직접 돌려 보고 출력으로 이해하는 방식)

```c
// loader.c - 셸코드 분석용 테스트 하네스 (격리 환경 전용)
#include <string.h>
#include <sys/mman.h>

unsigned char code[] = {
  0x48,0x31,0xf6,0x56,0x48,0xbf,0x2f,0x2f,0x62,0x69,0x6e,0x2f,
  0x73,0x68,0x57,0x54,0x5f,0x48,0x31,0xd2,0x6a,0x3b,0x58,0x0f,0x05
};

int main() {
    void *m = mmap(0, 4096, PROT_READ|PROT_WRITE|PROT_EXEC,
                   MAP_ANON|MAP_PRIVATE, -1, 0);   // RWX 메모리 (분석용)
    memcpy(m, code, sizeof(code));
    ((void(*)())m)();                               // 셸코드로 점프
    return 0;
}
```

```bash
gcc -z execstack loader.c -o loader
strace ./loader        # 어떤 syscall을 하는지 추적
```

`strace` 출력(핵심 부분)

```
mmap(NULL, 4096, PROT_READ|PROT_WRITE|PROT_EXEC, ...) = 0x7f...000
execve("//bin/sh", NULL, NULL)          ← 셸코드가 호출한 시스템 콜
...
```

- `execve("//bin/sh", NULL, NULL)` 한 줄이 셸코드의 정체를 그대로 보여준다.
- **분석 핵심**: `strace`의 syscall 한 줄 + `objdump`의 어셈블리를 교차 대조하면, 임의의 바이트 덩어리도 무엇을 하는 코드인지 복원할 수 있다.

```bash
# 바이트만 가지고 역으로 디스어셈블하는 연습 (정적 분석)
objdump -D -b binary -m i386:x86-64 sh.bin
# 또는
python3 -c "from pwn import *; context.arch='amd64'; print(disasm(open('sh.bin','rb').read()))"
```

### 4-4. NOP sled

- `\x90`(NOP, no-operation) 바이트를 셸코드 앞에 길게 붙인 것.
- 리턴 주소를 정확히 못 맞혀도 sled 어딘가에 착지하면 쭉 미끄러져 셸코드에 도달.
- ASLR 등장 이전, 스택 주소 불확실성을 완화하던 기법.

```
[   NOP   NOP   NOP   ...   NOP   ][   shellcode   ]
   \x90 \x90 ...                       \x48\x31...
   └── 어디에 착지해도 오른쪽으로 흘러 셸코드에 도달 ──┘
```

### 4-5. 셸코드 종류

| 종류 | 설명 |
| --- | --- |
| 로컬(local) | 로컬 권한 상승, 로컬 셸 획득 등 |
| 원격 - 바인드(bind) | 대상에 포트를 열고 공격자의 접속을 대기 |
| 원격 - 리버스(reverse) | 대상이 공격자에게 거꾸로 연결 (방화벽 우회에 유리) |
| 스테이저(stager) | 작은 1차 코드가 더 큰 2차 페이로드를 받아 실행 (길이 제한 회피) |
| egg-hunter | 메모리에서 미리 심어둔 큰 페이로드를 탐색해 실행 |

## 5. 완화 기법(Mitigations)과 우회 개념

현대 OS·컴파일러는 셸코드 기반 공격(데이터 영역에 코드 주입 후 실행)을 여러 보호 기법으로 크게 어렵게 만들었다. 각 기법이 무엇을 막고, 어떤 전제가 깨지면 우회되는지를 이해하는 것이 분석의 핵심이다.

| 보호 기법 | 주요 기능 | 셸코드에 미치는 영향 | 우회가 시도되는 방향 (개념) |
| --- | --- | --- | --- |
| **NX / DEP** | 스택·힙 등 데이터 영역을 실행 불가로 표시 | 스택에 올린 셸코드가 **실행 자체 불가** | 코드 주입 대신 **ROP / ret2libc** 로 기존 코드 재사용 |
| **ASLR** | 라이브러리·스택·힙 주소를 무작위화 | 리턴 주소/셸코드 위치를 **예측 불가** | 주소 **유출(info leak)** 로 베이스 계산 |
| **Stack Canary** | 리턴 주소 앞 랜덤 값, 리턴 전 검증 | RET 덮기 전에 변조 **탐지** | 카나리 값 **유출** 후 그대로 재기록 |
| **PIE** | 실행 파일 코드도 임의 주소에 배치 | 내부 함수·가젯의 고정 주소 사용 불가 | 코드 베이스 **유출** 후 오프셋 계산 |
| **RELRO** | GOT 등을 읽기 전용으로 | GOT overwrite 방어 | Full RELRO면 GOT 공격 차단 → 다른 벡터 |
| **CFI** | 간접 분기(call/jmp) 대상을 제한 | 비정상 제어 흐름 차단 | 허용된 흐름 내 가젯만 조합 시도 |

### DEP를 우회하는 ROP (Return-Oriented Programming)

- NX 때문에 새 코드를 주입해서 실행이 막히자, 이미 존재하는 코드 조각인 **Gadget**(보통 `...; ret`로 끝남)을 이어 붙여 원하는 동작을 구성하는 기법.
- 셸코드를 못 넣으면, 기존 코드로 프로그램을 재프로그래밍한다는 발상.
- 흔한 목표: `mprotect`를 ROP로 호출해 메모리를 실행 가능으로 바꾼 뒤 셸코드 실행, 또는 libc의 `system("/bin/sh")` 직접 호출(ret2libc).

> NX의 등장으로 고전적 스택 셸코드 실행은 대부분 막혔고, 공격은 **기존 코드 재사용(ROP)** 방향으로 진화했다.
또한 ASLR/PIE/Canary는 비밀(주소·값)에 의존하므로, 현대적 우회는 대부분 **정보 유출(info leak)** 에서 출발한다.
> 

※ 이 보호 기법들은 공격을 어렵게 만드는 방어 계층일 뿐, 근본 취약점을 제거하진 않는다. 여러 기법을 함께 적용하는 심층 방어가 중요하다.

## 6. 셸코드 분석 방법

주어진 바이트가 무슨 일을 하는지 읽어내는 것이 분석의 핵심이다.

### 6-1. 정적 분석 - 디스어셈블

```bash
objdump -D -b binary -m i386:x86-64 shellcode.bin
```

읽을 때 체크리스트

1. `RAX`(또는 `AL`)에 들어가는 **syscall 번호**는? → 무슨 시스템 콜인지 파악
2. 인자 레지스터(`RDI/RSI/RDX`)에 무엇이 세팅되는가?
3. `/bin/sh`, `/etc/passwd`, IP·포트 같은 **상수**가 보이는가?
4. `xor`/shift로 **금지 바이트를 회피**하거나, 디코더 루프로 **인코딩을 푸는** 패턴이 보이는가?

### 6-2. 동적 분석 - 실행 추적

```bash
strace ./harness    # 호출되는 syscall 실시간 관찰 (execve, connect, socket 등)
ltrace ./harness    # 라이브러리 함수 호출 관찰
```

GDB(pwndbg/gef)로 셸코드가 올라간 메모리에 중단점을 걸고 레지스터·스택을 단계 실행하며 확인한다.

### 6-3. 인코딩/난독화 식별

- 탐지·금지바이트 회피를 위해 셸코드는 **인코딩(예: XOR 디코더 + 암호화된 본문)** 되는 경우가 많다.
- <앞부분의 작은 디코더 루프 + 뒤의 암호화된 바이트 패턴>을 인지하면, 복호화 후 본문을 해석할 수 있다.
- 방어 관점: IDS/IPS·백신 시그니처가 이런 **다형성(polymorphic) 셸코드**에 어떻게 우회당하는지 이해하는 데 연결된다.

## 7. 셸코드와 관련 기법 비교

| 기법 | 핵심 아이디어 | 전제(필요 조건) |
| --- | --- | --- |
| **셸코드 주입** | 새 기계어를 메모리에 넣고 그곳으로 점프 | 해당 영역이 **실행 가능**(NX 비활성) |
| **ret2win** | 바이너리에 이미 있는 특정 함수로 점프 | 원하는 동작의 함수가 존재, 주소 파악 |
| **ret2libc** | libc의 `system("/bin/sh")` 등을 호출 | libc 주소 확보(ASLR 시 유출 필요) |
| **ROP** | 가젯(`...; ret`)을 이어 붙여 동작 구성 | 충분한 가젯, 스택 제어 |
- **셸코드 vs ROP**
    - 셸코드: 새 코드를 넣는다.
    - ROP: 기존 코드를 재사용한다.
    - NX 환경에서는 ROP가 기본 선택.
- **셸코드 vs ret2libc**
    - ret2libc는 셸코드 없이도 셸을 띄우는 대표적 코드 재사용 기법.

## 8. 셸코드의 보안상 영향 (CIA)

셸코드는 임의 코드 실행의 실행 본체이므로, 성공 시 보안의 3요소 전체를 침해할 수 있다.

### 8-1. 기밀성(Confidentiality)

- 셸 획득·파일 읽기 syscall로 인증 정보, 암호화 키, 개인정보 등 민감 데이터를 유출할 수 있다.

### 8-2. 무결성(Integrity)

- 파일 쓰기·프로세스 조작으로 시스템 설정·데이터를 변조하거나 백도어를 설치할 수 있다.

### 8-3. 가용성(Availability)

- 프로세스 종료·자원 고갈 등으로 서비스를 중단시킬 수 있다.

### 8-4. 권한 상승·지속성

- 권한 상승 셸코드로 더 높은 권한을 획득하거나, 리버스 셸로 지속적 접근 통로를 확보할 수 있다.

→ 실제 영향 범위는 **선행 취약점으로 제어 흐름을 얼마나 확실히 탈취했는지**와 **적용된 보호 기법**에 따라 달라진다.

## 9. 방어 방법

1. **근본 원인 제거**
    - 셸코드는 선행 취약점(BOF, OOB Write 등)이 있어야 전달·실행된다. → **메모리 손상 취약점 자체를 없애는 것**이 1순위.
    - 안전한 함수(`fgets`/`snprintf`), 입력 길이·인덱스 범위 검증.
2. **메모리 실행 정책 (코드 주입 차단)**
    - NX/DEP, W^X(쓰기·실행 동시 불가)를 기본 활성화한다.
    
    ```bash
    gcc -O2 -D_FORTIFY_SOURCE=2 -fstack-protector-strong \
        -fPIE -pie -Wl,-z,relro,-z,now,-z,noexecstack app.c -o app
    checksec --file=./app   # NX / Canary / PIE / Full RELRO 확인
    ```
    
3. **주소 예측 차단**
    - ASLR/PIE를 활성화하고, **정보 유출 취약점(포맷 스트링, OOB Read)** 을 함께 제거한다(유출이 막혀야 ASLR이 유효).
4. **메모리 안전성 확보**
    - 가능하면 Rust 등 메모리 안전 언어 사용.
    - 개발 시 **AddressSanitizer(ASan)**, 정적 분석, 퍼징(AFL++/libFuzzer)으로 경계 오류 탐지.
5. **탐지·대응 (방어 운영)**
    - IDS/IPS·EDR로 알려진 셸코드 패턴·비정상 syscall 시퀀스를 탐지한다.
    - 단, 인코딩/다형성 셸코드로 시그니처가 우회될 수 있음을 전제로 다층 방어를 구성한다.

## 11. 핵심 정리

> 셸코드는 메모리 손상 취약점으로 제어 흐름(`RIP`)을 탈취한 뒤 실행되는 **기계어 페이로드**이며,
취약점 그 자체가 아니라 익스플로잇의 **실행 단계** 구성 요소다.
> 
> 
> 입력 제약(길이·금지 바이트·위치 독립성)을 만족해야 하고, 결국 **시스템 콜**(`execve` 등)을 통해 동작한다.
> 분석의 핵심은 **바이트를 디스어셈블(objdump)하고 실행을 추적(strace)해, 어떤 syscall을 하는지 읽어내는 것**이다.
> 
> 현대 OS는 NX/DEP·ASLR·Stack Canary·PIE로 스택 셸코드 실행을 크게 어렵게 만들었고,
> 공격은 ROP처럼 **기존 코드를 재사용하는 방향**으로 진화했으며, 현대적 우회는 대부분 **정보 유출(info leak)** 에서 출발한다.
> 
> 핵심은, **셸코드를 막는 가장 확실한 방법은 셸코드를 전달하는 선행 취약점 자체를 제거하는 것이며,
> 그 위에 NX·ASLR 등 실행 정책과 주소 무작위화를 겹겹이 적용하는 심층 방어다.**
>
