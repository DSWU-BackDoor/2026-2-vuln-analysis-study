# Stack Canary

## 1. 개념

### 1-1. 스택 카나리란?

- **스택 카나리(Stack Canary)**는 스택 버퍼 오버플로우(BOF)로 **리턴 주소가 덮이는 것을 탐지**하기 위해, 컴파일러가 스택 프레임의 **지역 변수(버퍼)와 저장된 리턴 주소 사이에 심어 두는 랜덤 값**이다. 함수가 반환되기 직전에 이 값이 바뀌었는지 검사하여, 변조가 감지되면 프로그램을 즉시 종료한다.
- **이름의 유래**: 광부들이 유독가스를 먼저 감지하려고 갱도에 데려가던 **카나리아(canary)** 에서 유래했다. 리턴 주소가 오염되기 전에 카나리 값이 먼저 죽어서(변조되어) 위험을 알린다는 발상이다. (스택 스매싱 보호에서는 **스택 쿠키(stack cookie)** 라고도 부른다.)
- **분류**: 카나리는 취약점(CWE)이 아니라 **완화 기법(mitigation)** 이다. 특히 CWE-121(Stack-based Buffer Overflow), CWE-787(Out-of-bounds Write)로 리턴 주소를 덮는 공격을 탐지하는 방어 계층이다.
- **핵심 성격**: 카나리는 오버플로우 자체를 막지 못한다. 버퍼는 여전히 넘칠 수 있다. 다만 리턴 주소를 넘어서 덮으려면 반드시 그 사이의 카나리를 거쳐야 하므로, 리턴 전에 변조를 탐지하는 것이다.
- **형태**: 함수 진입 시 스택에 저장되고 함수 종료 직전 검증되는 고정 크기의 값. x86-64 기준 보통 8바이트, 그중 최상위(또는 최하위) 1바이트는 `0x00`으로 고정된다.

### 1-2. 전체 공격 체인에서의 위치

카나리는 공격 체인의 제어 흐름 탈취 단계에서 작동하는 탐지기다.

```
취약점(BOF) → [리턴 주소 덮기 시도] → 제어 흐름 탈취 → 페이로드(shellcode/ROP)
    │                 │                      │                  │
 버퍼 넘침     카나리를 밟고 지나감      ←── 여기서 탐지 ──→   (도달 못함)
                      │
              RET 직전 카나리 검증 실패 → __stack_chk_fail() → abort
```

→ 즉 카나리는 **버그(오버플로우)는 허용하되, 그것이 제어 흐름 탈취로 이어지는 길을 차단**한다. 공격이 성공하려면 공격자는 카나리 값을 알아내서 그대로 다시 써 넣어야 한다.

## 2. 배경 지식

### 2-1. 스택 프레임 구조와 카나리의 위치

카나리의 동작은 **스택 프레임 안에서 카나리가 어디에 놓이는가**로 결정된다. x86-64 기준, 스택은 높은 주소 → 낮은 주소로 자란다.

```
높은 주소
┌─────────────────────────┐
│   함수 인자 / 호출자     │
├─────────────────────────┤
│   저장된 리턴 주소(RET)  │  ← 공격자의 최종 목표
├─────────────────────────┤
│   저장된 RBP            │
├─────────────────────────┤
│   ★ 스택 카나리 ★      │  ← 버퍼와 RET 사이
├─────────────────────────┤
│   지역 버퍼 char buf[]  │  ← 오버플로우 시작점 (낮은 주소)
└─────────────────────────┘
낮은 주소

     overflow 진행 방향 ───────────→ (낮은 주소 → 높은 주소로 덮임)
```

- 버퍼가 넘치면 **반드시 카나리를 먼저 지나야** RBP·RET에 도달한다.
- 따라서 RET를 덮으려는 오버플로우는 거의 항상 카나리를 변조하게 되고, 검증 단계에서 걸린다.

### 2-2. 카나리 값의 종류

| 종류 | 형태 | 특징 |
| --- | --- | --- |
| **Terminator 카나리** | `0x00 0x0d 0x0a 0xff` 등 종결 바이트 포함 | `strcpy`(`\x00`), `gets`(`\x0a`) 등 문자열 함수가 멈추는 바이트로 구성 → 문자열 복사로는 덮기 어려움 |
| **Random 카나리** | 프로세스 시작 시 난수로 생성 | 현대 리눅스의 기본. 예측 불가가 핵심 방어력 |
| **Random XOR 카나리** | 난수 ⊕ 제어 데이터(RET 등) | 값 유출뿐 아니라 제어 데이터 무결성까지 묶음 |

- **리눅스 glibc의 핵심 특징**: 랜덤 카나리의 **최하위 바이트(LSB)가 `0x00`(널 바이트)** 로 고정된다. 이는 문자열 함수가 카나리를 읽어서 유출하는 것을 어렵게 만드는 장치지만, 동시에 유출 시 맨 끝 `00` 을 식별하는 단서가 되기도 한다.

### 2-3. 카나리는 어디에 저장되는가 (TLS)

- 각 스레드의 **카나리 원본(master canary)** 은 **TLS(Thread Local Storage)** 영역에 저장된다. x86-64 리눅스에서는 세그먼트 레지스터 **`fs`** 가 가리키는 TLS 블록의 **`fs:0x28`** 오프셋에 위치한다.
- 함수 진입(프롤로그) 시 `fs:0x28`에서 값을 읽어 스택에 복사하고, 함수 종료(에필로그) 시 스택의 값을 다시 `fs:0x28`과 비교한다.
- 스택의 복사본만 고쳐도 소용없고, 공격자가 TLS의 원본을 덮어쓰거나(특정 조건) 스택 복사본과 원본을 동시에 일치시켜야 한다.

## 3. 카나리 동작 원리 (컴파일러가 삽입하는 코드)

컴파일러(`-fstack-protector` 계열)는 보호 대상 함수에 **프롤로그(설치)** 와 **에필로그(검증)** 코드를 자동으로 끼워 넣는다.

### 3-1. 프롤로그 (카나리 설치)

```nasm
; 함수 시작부
mov    rax, qword ptr fs:[0x28]   ; TLS에서 master canary 로드
mov    qword ptr [rbp-0x8], rax   ; 스택 프레임(버퍼 위)에 카나리 복사
xor    eax, eax                   ; 흔적 제거(레지스터에 카나리 안 남김)
```

### 3-2. 에필로그 (카나리 검증)

```nasm
; 함수 반환 직전
mov    rax, qword ptr [rbp-0x8]   ; 스택에 있던 카나리 값 읽기
sub    rax, qword ptr fs:[0x28]   ; 원본과 비교 (xor로 구현되기도 함)
je     .return_ok                 ; 같으면 정상 → 반환 진행
call   __stack_chk_fail           ; 다르면 변조 → 종료 루틴
.return_ok:
    leave
    ret
```

- **검증 실패 시**: `__stack_chk_fail()` 이 호출되어 **`stack smashing detected`** 메시지를 출력하고 `abort()` 로 프로세스를 강제 종료한다. → 공격자는 **셸코드/ROP가 실행되기 전에** 차단된다.

### 3-3. 분석 포인트

- `fs:[0x28]` 패턴이 보이면 이 함수는 카나리로 보호되고 있다는 신호다.
- `__stack_chk_fail` 심볼이 바이너리에 있으면 SSP(Stack Smashing Protector)가 적용된 것이다. `checksec`의 `Canary found` 가 이를 요약해 준다.

## 4. 컴파일러 옵션 (어떤 함수가 보호되는가)

카나리는 모든 함수에 붙지 않는다. 성능 비용 때문에 컴파일러가 위험해 보이는 함수를 골라서 적용한다.

| 옵션 | 보호 대상 | 비고 |
| --- | --- | --- |
| `-fno-stack-protector` | 없음 | 카나리 **비활성** (실습/취약 코드) |
| `-fstack-protector` | `char buf[8]` 이상 등 문자열 버퍼를 가진 함수 | 보호 범위 좁음 |
| **`-fstack-protector-strong`** | 배열·주소 참조 지역변수 등을 폭넓게 가진 함수 | **현대 배포판 기본값**, 권장 |
| `-fstack-protector-all` | **모든** 함수 | 가장 강하지만 오버헤드 큼 |

```bash
# 카나리 적용/미적용 비교 컴파일
gcc -fstack-protector-strong vuln.c -o vuln_canary
gcc -fno-stack-protector     vuln.c -o vuln_nocanary

checksec --file=./vuln_canary   # "Canary found" 여부 확인
```

→ 분석 시 **보호받지 못하는 함수**를 찾는 것이 공격자의 한 갈래다. 버퍼 뒤에 카나리가 없는 함수라면 그 함수의 BOF는 바로 RET를 덮을 수 있다.

## 5. 카나리 우회 기법

카나리는 **비밀 값(랜덤)에 의존**하는 방어다. 따라서 우회는 대부분 값을 알아내거나 검증 자체를 건너뛰는 방향이다. (현대적 우회는 대부분 **정보 유출(info leak)** 에서 출발한다.)

### 5-1. 카나리 유출 (Info Leak)

카나리 값을 읽어낸 뒤, 오버플로우 페이로드의 카나리 자리에 **원래 값을 그대로 다시 써 넣어** 검증을 통과시킨다.

- **포맷 스트링 버그**: `printf(user_input)` 같은 취약점으로 `%p`·`%lx` 를 이용해 스택에 있는 카나리 값을 직접 출력시킨다.

    ```
    입력:  %p %p %p %p ...
    출력:  ... 0x7ffd... [카나리값] ...   ← 스택 덤프에서 끝자리가 00인 값을 찾음
    ```

- **오버리드(OOB Read) / 미초기화 출력**: 버퍼를 널 종료 없이 출력하는 함수(`printf("%s", buf)`)에서, 카나리 바로 앞까지 꽉 채워 **인접한 카나리까지 흘려 읽게** 만든다. (단, 카나리 LSB=`00` 때문에 맨 앞 1바이트는 가려질 수 있음)

### 5-2. 카나리 덮고 그대로 복원 (Overwrite & Rewrite)

5-1로 알아낸 카나리 값을, BOF 페이로드에서 **원래 자리에 똑같이 배치**한다.

```
[ buf 채움 ... ][ 유출한 카나리 값 그대로 ][ 가짜 RBP ][ 원하는 RET 주소 ]
```

→ 검증 단계에서 `스택 카나리 == 원본` 이 성립 → `__stack_chk_fail` 을 건너뛰고 조작된 RET로 반환.

### 5-3. Bruteforce (Byte-by-Byte, fork 서버 한정)

- **전제**: `fork()` 로 자식 프로세스를 띄우는 서버는 자식이 **부모의 카나리를 그대로 상속**한다(값이 바뀌지 않음). 자식이 죽어도 부모는 살아 있어 같은 카나리로 재시도 가능.
- **방법**: 카나리를 **1바이트씩** 덮어 보며, 크래시가 안 나면 그 바이트가 맞은 것. 8바이트면 최악 `256 × 8 = 2048`번으로 전수 가능(브루트포스 공간이 2^64가 아니라 8×2^8로 줄어든다).
- LSB가 `00`이라는 점을 이용하면 첫 바이트는 추정 가능.

### 5-4. 검증 자체를 건너뛰기

- **카나리 미보호 함수 공략**: 4장처럼 카나리가 안 붙은 함수의 BOF를 찾는다.
- **RET를 거치지 않는 제어 흐름 탈취**: 카나리는 **함수 에필로그의 RET 시점**에만 검사한다. 따라서
    - **함수 포인터 / 가상 함수 테이블(vtable) 덮어쓰기**,
    - **저장된 예외 핸들러(SEH, Windows)**,
    - **스택 프레임 내 다른 포인터 변수** 를 덮어 간접 호출을 탈취하면 RET 검증 전에 분기할 수 있다.
- **`__stack_chk_fail` 자체를 후킹/무력화** (GOT overwrite 등, Partial RELRO 조건).

### 5-5. TLS 원본(master canary) 덮어쓰기

- `fs:0x28`의 원본과 스택 복사본을 **둘 다 같은 임의 값으로** 맞출 수 있는 특수한 쓰기 primitive가 있으면, 검증은 통과하면서 값은 공격자가 아는 값이 된다. (난이도 높음, 특정 상황 한정)

> **요약**: 카나리의 방어력 = 값의 비밀성. 비밀이 **유출(5-1)** 되면 **복원(5-2)** 으로 그대로 뚫리고, fork 서버면 **Bruteforce(5-3)** 가, 설계적으로는 **RET를 안 거치는 경로(5-4)** 가 열려 있다.

## 6. 카나리와 다른 완화 기법의 관계

카나리는 단독 방어가 아니라 심층 방어(defense in depth)의 한 층이다. 다른 기법과 서로를 보완한다.

| 기법 | 막는 것 | 카나리와의 관계 |
| --- | --- | --- |
| **Stack Canary** | 리턴 주소 덮기 탐지 | 오버플로우 자체는 못 막음. 값 유출되면 무력화 |
| **NX / DEP** | 스택 셸코드 실행 | 카나리를 뚫어도 NX면 ROP/ret2libc로 전환 필요 |
| **ASLR / PIE** | 주소 예측 | 카나리·ASLR 모두 비밀 유출에 취약 → 둘 다 info leak이 관건 |
| **RELRO (Full)** | GOT overwrite | `__stack_chk_fail` GOT 후킹식 우회를 차단 |
| **CFI / shadow stack** | 비정상 간접 분기·RET | 카나리가 놓치는 RET 안 거치는 탈취를 보완 |

- **셸코드/ROP 관점**: 카나리는 셸코드 공격의 첫 관문(제어 흐름 탈취)을 막는다. 공격자는 (1) 카나리 유출로 관문 통과 → (2) NX 때문에 셸코드 대신 ROP → (3) ASLR 때문에 또 info leak, 순으로 여러 완화를 연쇄적으로 뚫어야 한다.
- **Intel CET / Shadow Stack**: 하드웨어가 리턴 주소의 사본을 별도 보호 영역(shadow stack)에 두고 RET마다 대조한다. 카나리의 값 유출 약점을 보완하는 차세대 방어다.

## 7. 카나리의 한계

1. **오버플로우 자체를 막지 못한다**
    - 버퍼는 넘치고, 인접 지역변수·구조체 멤버는 여전히 변조된다 (카나리 **아래쪽** 데이터)
2. **값이 유출되면 그대로 무력화**
    - 비밀성에 전적으로 의존.
3. **RET를 거치지 않는 제어 흐름 탈취**는 검사 시점 밖이다 (함수 포인터·vtable·longjmp buffer 등)
4. **오버라이트가 아닌 공격**(OOB Write로 카나리를 건너뛰고 특정 오프셋만 정밀하게 덮는 경우)엔 무력할 수 있다.
5. **미보호 함수**(옵션·휴리스틱상 카나리가 안 붙은 함수)의 BOF는 그대로 뚫린다.

## 8. 방어 방법 (운영/개발 관점)

1. **근본 원인 제거 (1순위)**
    - 카나리는 탐지기일 뿐, 취약점을 없애는 것이 최선. 안전한 함수(`fgets`/`snprintf`/`strncpy`), 입력 길이·인덱스 검증.
2. **카나리를 강하게 켠다**

    ```bash
    gcc -O2 -D_FORTIFY_SOURCE=2 -fstack-protector-strong \
        -fPIE -pie -Wl,-z,relro,-z,now,-z,noexecstack app.c -o app
    checksec --file=./app   # Canary / NX / PIE / Full RELRO 확인
    ```

    - `fstack-protector-strong`(또는 민감 바이너리는 `all`), `_FORTIFY_SOURCE`로 위험 함수 보강.
3. **유출 경로를 함께 막는다**
    - 카나리는 비밀 유지가 생명. **포맷 스트링·OOB Read** 같은 정보 유출 취약점을 반드시 제거(유출이 막혀야 카나리가 유효).
4. **심층 방어 중첩**
    - NX·ASLR·PIE·Full RELRO·CET(shadow stack)를 함께 적용. 한 층이 뚫려도 다음 층이 막도록.
5. **메모리 안전성 확보**
    - 가능하면 Rust 등 메모리 안전 언어. 개발 시 **ASan**, 정적 분석, 퍼징(AFL++/libFuzzer)으로 경계 오류 사전 탐지.
6. **탐지·대응**
    - `__stack_chk_fail`/`abort` 발생, 반복 크래시(브루트포스 징후)를 로깅·모니터링. fork 서버는 자식 크래시 급증을 이상 신호로 탐지.

## 9. 핵심 정리

> **스택 카나리는 버퍼와 리턴 주소 사이에 심은 랜덤 값으로, 함수 반환 직전에 변조 여부를 검사해 BOF에 의한 제어 흐름 탈취를 탐지하는 완화 기법**이다. 오버플로우 자체를 막는 것이 아니라, 버퍼와 리턴 주소 사이에 카나리를 두어 리턴 주소를 덮으려면 반드시 그 값까지 변조하게 만들고, **RET 시점의 검증으로 이를 탐지**해 `__stack_chk_fail`로 프로세스를 종료시킨다.
>
> 구현은 컴파일러(`-fstack-protector-*`)가 프롤로그에서 `fs:0x28`(TLS)의 값을 스택에 복사하고, 에필로그에서 다시 대조하는 식이다. 리눅스 랜덤 카나리는 **LSB가 `0x00`** 이라는 특징이 있다.
>
> 카나리의 방어력은 **값의 비밀성**에 전적으로 의존한다. 따라서 우회는 대부분 **정보 유출(포맷 스트링·OOB Read)로 값을 알아낸 뒤 오버플로우 때 그대로 복원**하는 것이며, fork 서버에서는 **바이트 단위 브루트포스**, 설계적으로는 **RET를 거치지 않는 경로(함수 포인터·vtable)** 가 틈이다.
>
> 핵심은, **카나리는 단독 방어가 아니라 NX·ASLR·PIE·RELRO·CET와 함께 쌓는 심층 방어의 한 층**이며, **가장 확실한 대책은 애초에 오버플로우를 만드는 취약점과 그 값을 흘리는 정보 유출 취약점을 함께 제거하는 것**이다.
