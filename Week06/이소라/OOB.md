# 시스템 취약점 분석 스터디 노트 — Out-of-Bounds (OOB)

> CWE-787 (Out-of-bounds Write)은 CWE Top 25 (2023, 2024)에서 **1위**, CWE-125 (Out-of-bounds Read)는 상위권에 오르는 메모리 손상 취약점이다.

---

## 1. 개념

**배열이나 버퍼의 유효한 범위(인덱스 0 ~ 길이-1) 밖의 메모리에 접근하는 것이다.**

- **OOB Read** 는 범위 밖의 메모리를 **읽는** 것이다 → 정보 유출 (CWE-125).
- **OOB Write** 는 범위 밖의 메모리에 **쓰는** 것이다 → 메모리 변조, 실행 흐름 탈취 (CWE-787).

> Buffer Overflow와의 차이: Buffer Overflow는 보통 **연속으로 넘쳐서** 인접 메모리를 덮는다. OOB는 **인덱스 계산이 잘못되어** 원하는 위치 한 곳을 **골라서(임의 위치)** 읽거나 쓸 수 있다는 점이 핵심이다. 넓게 보면 Buffer Overflow도 OOB Write의 한 형태다.

C/C++은 배열 접근 시 인덱스 범위를 자동으로 검사하지 않는다. `arr[idx]`는 단지 `*(arr + idx * sizeof(원소))` 주소 계산일 뿐이므로, `idx`가 범위를 벗어나도 그 주소에 그대로 접근한다.

---

## 2. 구조 — 인덱스와 주소 계산

```c
int arr[10];   // arr의 시작 주소가 0x1000이라고 하자 (int = 4바이트)
```

| 접근       | 계산되는 주소              | 결과                       |
| ---------- | -------------------------- | -------------------------- |
| `arr[0]`   | 0x1000 + 0 × 4 = 0x1000    | 정상                       |
| `arr[9]`   | 0x1000 + 9 × 4 = 0x1024    | 정상 (마지막 원소)         |
| `arr[10]`  | 0x1000 + 10 × 4 = 0x1028   | **OOB** (배열 바로 뒤)     |
| `arr[-1]`  | 0x1000 + (-1) × 4 = 0x0FFC | **OOB** (배열 바로 앞)     |
| `arr[100]` | 0x1000 + 100 × 4 = 0x1190  | **OOB** (멀리 떨어진 위치) |

> 핵심은 "**인덱스를 조작하면 배열 기준 상대 주소로 어디든 접근할 수 있다**"는 것이다. 음수 인덱스로 배열 **앞쪽** 메모리도 건드릴 수 있다.

---

## 3. 발생 원인

| 원인                   | 설명                                                                     | 예시                                          |
| ---------------------- | ------------------------------------------------------------------------ | --------------------------------------------- |
| 상한만 검사            | `idx < size`만 확인하고 `idx >= 0`은 확인하지 않는다                     | `if (idx < 10) arr[idx]` → `idx = -5` 통과    |
| 경계 검사 누락         | 사용자 입력 인덱스를 아무 검사 없이 사용한다                             | `arr[user_input]`                             |
| Off-by-One             | `<` 대신 `<=`를 써서 1칸 넘는다                                          | `for (i = 0; i <= 10; i++)`                   |
| 부호 혼동 (Signedness) | signed/unsigned 비교나 변환에서 음수가 큰 양수로 바뀌거나 그 반대가 된다 | `int len = -1` → `size_t`로 바뀌면 매우 큰 값 |
| 정수 오버플로          | 크기·인덱스 계산 중 값이 넘쳐 작은 값이 되어 검사를 통과한다             | `count * size`가 넘쳐 작은 버퍼가 할당된다    |
| 길이 필드 신뢰         | 패킷이나 파일 안의 길이 값을 그대로 믿는다                               | Heartbleed (아래 참고)                        |

### 취약한 코드 예시

```c
char *menu[4] = {"coffee", "tea", "juice", "water"};

void order(int idx) {
    if (idx < 4)                       // 음수 검사가 없다
        printf("%s\n", menu[idx]);     // idx = -3 이면 배열 앞쪽 메모리를 읽는다
}
```

### 안전한 코드 예시

```c
void order(int idx) {
    if (idx < 0 || idx >= (int)(sizeof(menu) / sizeof(menu[0])))
        return;                        // 하한과 상한을 모두 검사한다
    printf("%s\n", menu[idx]);
}
```

> 더 간단한 방법은 인덱스를 **unsigned**(`size_t`)로 받는 것이다. 음수가 들어올 수 없으므로 상한만 검사하면 된다.

## 4. 대표 공격 유형

### (1) OOB Read — 정보 유출 (Information Leak)

범위 밖의 메모리를 읽어 민감 정보를 얻는다.

- 다른 변수에 있는 **비밀값, 플래그, 키**를 읽는다.
- **스택 카나리, 라이브러리 주소, 스택 주소**를 유출해 Canary·ASLR·PIE 같은 보호 기법을 우회하는 발판으로 쓴다.

> 단독으로는 "읽기만" 하지만, 실제 공격에서는 OOB Write나 Buffer Overflow와 **연계하는 첫 단계**가 되는 경우가 많다.

### (2) OOB Write — 임의 위치 쓰기

인덱스를 조작해 원하는 위치에 값을 쓴다.

- 인접한 **지역 변수, 전역 변수**(예: 권한 플래그)를 바꾼다.
- **함수 포인터, GOT 엔트리, 리턴 주소**를 덮어 실행 흐름을 바꾼다.

```
배열 기준 상대 위치를 계산 → 인덱스 = (목표 주소 - 배열 시작 주소) / 원소 크기
```

> Buffer Overflow는 사이에 있는 카나리까지 연속으로 덮어 탐지되지만, OOB Write는 **카나리를 건너뛰고 목표만 정확히 덮을 수 있다.** 그래서 Stack Canary로는 막기 어렵다.

### (3) 음수 인덱스 (Negative Index)

하한 검사가 빠진 경우 음수를 넣어 **배열 앞쪽**에 있는 데이터(다른 변수, 구조체 멤버, 힙 청크 헤더 등)에 접근한다. 드림핵 `out_of_bound` 같은 워게임의 단골 패턴이다.

### (4) 정수 오버플로 연계

크기 계산이 넘쳐서 실제보다 **작은 버퍼**가 할당되고, 이후 원래 크기만큼 쓰면서 OOB Write가 발생한다.

```c
buf = malloc(count * sizeof(item));   // count가 크면 곱셈이 넘쳐 작은 값이 된다
for (i = 0; i < count; i++) buf[i] = ...;   // 할당 크기를 넘어서 쓴다
```

### (5) 실제 사례 — Heartbleed (CVE-2014-0160)

OpenSSL의 Heartbeat 기능에서 클라이언트가 보낸 **길이 필드를 검증하지 않고** 그 길이만큼 메모리를 복사해 응답했다.
실제 데이터는 짧은데 길이를 크게 적으면, 서버 메모리(개인키, 세션 쿠키, 비밀번호 등)가 최대 64KB씩 유출됐다. **OOB Read의 대표 사례**다.

## 5. 꼭 알아두기

- **OOB Read = 유출, OOB Write = 변조**로 구분한다. CWE 번호도 다르다 (125 / 787).
- **인덱스 검사는 하한(0 이상)과 상한(길이 미만)을 둘 다 한다.** 상한만 검사하는 코드가 가장 흔한 실수다.
- **signed와 unsigned를 섞지 않는다.** 비교·변환 과정에서 음수가 큰 양수로 바뀌어 검사를 통과할 수 있다.
- **Buffer Overflow와 비교**는 시험 단골!

| 구분         | Buffer Overflow                      | Out-of-Bounds                               |
| ------------ | ------------------------------------ | ------------------------------------------- |
| 접근 방식    | 연속으로 넘쳐서 인접 메모리를 덮는다 | 인덱스·포인터 계산으로 특정 위치에 접근한다 |
| 접근 위치    | 버퍼 뒤쪽(인접 영역)                 | 앞뒤 어디든 가능 (음수 인덱스 포함)         |
| 주 원인      | 길이 검사 없는 복사 함수             | 인덱스 범위 검사 누락, 정수 문제            |
| Stack Canary | 탐지 가능                            | 건너뛸 수 있어 탐지가 어렵다                |
| 읽기/쓰기    | 주로 쓰기                            | 읽기(유출)와 쓰기(변조) 모두                |

- 보호 기법별 효과도 정리한다.

| 보호 기법                                  | OOB에 대한 효과                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| **Stack Canary**                           | 카나리를 건너뛰는 OOB Write는 막지 못한다                                                                    |
| **ASLR / PIE**                             | 절대 주소를 모르게 하지만, 배열 기준 **상대 위치** 접근은 막지 못한다. OOB Read로 주소가 유출되면 무력화된다 |
| **NX / DEP**                               | 쉘코드 실행은 막지만, 데이터 변조나 ROP는 막지 못한다                                                        |
| **RELRO (Full)**                           | GOT 덮어쓰기를 막는다                                                                                        |
| **Bounds Checking** (ASan, 언어 차원 검사) | 범위 밖 접근 자체를 탐지·차단한다. **근본적인 대책**이다                                                     |

---

## 6. 방어 (Mitigation)

1. **모든 인덱스에 하한과 상한을 검사한다.** `0 <= idx && idx < len` 형태로 둘 다 확인한다.
2. **인덱스와 크기는 unsigned(`size_t`)로 다룬다.** signed/unsigned 혼용 비교를 피하고 컴파일러 경고(`-Wall -Wextra -Wsign-compare`)를 켠다.
3. **배열 길이는 하드코딩하지 않고 계산한다.** `sizeof(arr) / sizeof(arr[0])`이나 상수 매크로를 한 곳에서 관리한다.
4. **외부 입력의 길이 필드를 신뢰하지 않는다.** 실제 수신한 데이터 크기와 비교해 검증한다 (Heartbleed의 교훈).
5. **크기 계산 시 정수 오버플로를 검사한다.** `calloc()`이나 `__builtin_mul_overflow()`처럼 오버플로를 확인하는 방식을 쓴다.
6. **런타임 검사 도구를 사용한다.** AddressSanitizer(`-fsanitize=address`), UBSan(`-fsanitize=undefined`), 퍼징(AFL++, libFuzzer)으로 개발 단계에서 잡는다.
7. **경계 검사를 해주는 자료구조나 언어를 쓴다.** C++의 `std::vector::at()`, `std::span`, 또는 Rust·Java·Go처럼 범위 밖 접근을 런타임에 막는 메모리 안전 언어를 고려한다.
8. **Full RELRO, ASLR/PIE 등 보호 기법을 함께 적용**해 OOB가 발생해도 악용을 어렵게 만든다 (Defense in Depth).
