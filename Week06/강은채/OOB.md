# OOB (Out-of-Bounds)

## 1. 개념

### 1-1. OOB란?

**OOB(Out-of-Bounds)**는 프로그램이 배열(Array), 버퍼(Buffer) 등 할당된 메모리 객체의 유효한 범위를 벗어나 메모리에 접근하는 취약점이다.

일반적으로 배열이나 버퍼는 특정 크기의 메모리 공간을 할당받으며, 해당 공간 내에서만 데이터를 읽거나 쓸 수 있다. 그러나 프로그램이 입력값이나 인덱스에 대한 범위 검증을 제대로 수행하지 않으면 허용된 범위를 벗어난 메모리에 접근할 수 있다.

OOB는 크게 두 가지 유형으로 구분된다.

- **OOB Read**: 유효한 메모리 범위를 벗어난 위치에서 데이터를 읽는 경우
- **OOB Write**: 유효한 메모리 범위를 벗어난 위치에 데이터를 쓰는 경우

예를 들어 크기가 5인 정수형 배열이 존재한다고 가정한다.

```c
int arr[5] = {10, 20, 30, 40, 50};
```

배열의 인덱스는 0부터 시작하므로 유효한 인덱스 범위는 0~4이다.

| 인덱스 | 접근 가능 여부 |
| --- | --- |
| arr[0] ~ arr[4] | 정상 접근 |
| arr[5] | 범위 초과 |
| arr[-1] | 범위 이전 |

`arr[5]` 또는 `arr[-1]`과 같이 유효한 범위를 벗어난 인덱스를 사용하면 OOB가 발생할 수 있다.

※ OOB는 단순히 배열의 인덱스를 잘못 사용하는 경우에만 발생하는 것은 아니다. 포인터 연산, 버퍼 크기 계산, 파일 및 네트워크 데이터 처리 과정에서도 발생할 수 있다.

### 1-2. OOB 발생 원리

프로그램은 메모리에 데이터를 저장하고 읽기 위해 배열의 인덱스나 포인터를 사용한다. 이때 접근하려는 메모리 주소가 해당 객체에 할당된 유효한 범위에 포함되는지 확인해야 하지만, 범위 검증이 누락되거나 잘못된 크기 계산이 수행되면 의도된 메모리 영역을 벗어나 접근하게 된다.

1. 프로그램이 배열 또는 버퍼에 메모리 공간을 할당한다.
2. 사용자 입력이나 내부 연산을 통해 접근할 인덱스 또는 주소가 결정된다.
3. 해당 값에 대한 유효성 검증이 제대로 수행되지 않는다.
4. 프로그램이 유효한 메모리 범위를 벗어난 위치에 접근한다.
5. 메모리 읽기 또는 쓰기 과정에서 예상하지 못한 동작이 발생한다.

→ 프로그램의 메모리 구조와 실행 환경에 따라 정보 노출, 메모리 손상, 프로그램 비정상 종료 등의 결과로 이어질 수 있다.

## 2. OOB의 종류

### 2-1. OOB Read

할당된 메모리 범위를 벗어난 위치에서 데이터를 읽는 취약점이다. 배열의 유효한 인덱스 범위를 확인하지 않고 데이터를 읽거나, 버퍼의 크기를 초과하는 길이만큼 데이터를 읽으려고 할 때 발생할 수 있다.

**발생 예시**

- 배열의 범위를 벗어난 인덱스로 데이터 조회
- 버퍼의 끝을 넘어서는 데이터 읽기
- 잘못된 포인터 연산을 통한 메모리 접근
- 문자열의 종료 문자를 확인하지 않고 메모리를 계속 읽는 경우

**주요 영향**

1. **정보 노출(Information Disclosure)**: 인증 정보, 암호화 키, 개인정보 등 메모리에 저장된 민감한 정보가 노출될 수 있다.
2. **메모리 주소 노출**: 프로세스 메모리의 주소 정보가 노출되어 ASLR(Address Space Layout Randomization) 같은 보호 기법을 우회하기 위한 추가 정보로 활용될 수 있다.
3. **서비스 거부(DoS)**: 접근할 수 없는 메모리 영역을 읽으려 하면 프로그램이 비정상 종료될 수 있다.

→ 메모리를 직접 수정하지 않더라도 내부 정보를 외부로 노출시킬 수 있다는 점에서 위험하다.

### 2-2. OOB Write

할당된 메모리 범위를 벗어난 위치에 데이터를 쓰는 취약점이다. 배열이나 버퍼의 크기를 초과하는 데이터를 기록하거나, 잘못된 인덱스를 통해 메모리 값을 변경할 때 발생할 수 있다.

**발생 예시**

- 배열의 범위를 벗어난 인덱스에 데이터 저장
- 버퍼의 크기보다 큰 데이터를 기록
- 잘못된 포인터 연산을 통해 의도하지 않은 메모리 위치에 데이터 저장
- 입력값에 따라 메모리 쓰기 위치가 잘못 계산되는 경우

**주요 영향**

1. **메모리 손상(Memory Corruption)**: 인접한 변수나 데이터 구조가 변경·손상될 수 있다.
2. **프로그램 비정상 종료**: 중요한 메모리 데이터가 손상되면서 프로그램이 정상적으로 동작하지 못할 수 있다.
3. **실행 흐름 변조**: 함수 포인터, 반환 주소 등 제어 흐름 관련 데이터가 손상되면 비인가 코드 실행으로 이어질 가능성이 있다.

### 2-3. OOB Read와 OOB Write 비교

| 구분 | OOB Read | OOB Write |
| --- | --- | --- |
| 정의 | 범위 밖의 메모리 읽기 | 범위 밖의 메모리 쓰기 |
| 주요 동작 | 데이터 조회 | 데이터 변경 |
| 주요 위험 | 정보 노출 | 메모리 손상 |
| 발생 결과 | 민감 정보 노출, 크래시 | 메모리 변조, 크래시 |
| CWE | CWE-125 | CWE-787 |

두 취약점 모두 메모리 접근 범위 검증이 제대로 이루어지지 않아 발생한다는 공통점이 있다.

## 3. OOB 발생 원인

OOB는 다양한 프로그래밍 오류로 인해 발생할 수 있으며, 특히 C/C++처럼 프로그래머가 메모리 접근과 포인터 연산을 직접 관리하는 언어에서 주의해야 한다.

### 3-1. 배열 인덱스 범위 검증 누락

배열의 크기가 N이라면 유효한 인덱스 범위는 0부터 N-1까지이다. 사용자 입력이나 외부 데이터에서 전달된 인덱스를 검증 없이 사용하면 배열의 범위를 벗어난 메모리에 접근할 수 있다. 특히 **음수 인덱스 검증**을 빠뜨리거나, 마지막 인덱스보다 큰 값을 허용하는 경우 문제가 발생한다.

### 3-2. 입력 데이터 길이 검증 실패

예를 들어 100바이트 버퍼를 할당했는데 외부에서 전달된 데이터가 200바이트라면 버퍼의 유효 범위를 벗어나는 접근이 발생한다. 다음과 같은 환경에서 자주 발생한다.

- 파일 파서(File Parser)
- 네트워크 패킷 처리 프로그램
- 이미지 및 미디어 처리 라이브러리
- 압축 파일 처리 프로그램

특히 파일이나 네트워크 데이터의 **헤더에 포함된 길이 정보를 신뢰**하고 실제 데이터 크기와 비교하지 않으면 OOB가 발생할 가능성이 높다.

### 3-3. 정수 오버플로우(Integer Overflow) 및 언더플로우(Integer Underflow)

메모리를 할당하거나 접근할 위치를 계산하는 과정에서 정수 오버플로우/언더플로우가 발생하면 잘못된 크기나 주소가 계산될 수 있다.

**Integer Overflow**: 정수형 변수가 표현할 수 있는 최댓값을 초과하는 연산으로 예상과 다른 값이 되는 현상

```c
unsigned int size = 0xFFFFFFFF;
size = size + 1;   // size == 0
```

**Integer Underflow**: 정수형 변수가 표현할 수 있는 최솟값보다 작아져 예상과 다른 값이 되는 현상

```c
unsigned int size = 0;
size = size - 1;   // size == 0xFFFFFFFF
```

그 결과 실제 버퍼 크기와 프로그램이 인식하는 크기 사이에 차이가 생기고, 유효 범위를 벗어난 메모리 접근으로 이어질 수 있다.

※ **부호 없는(unsigned) 정수**의 오버플로우/언더플로우는 C 표준상 값이 순환(wraparound)하도록 정의되어 있다. 반면 **부호 있는(signed) 정수**의 오버플로우는 **미정의 동작(Undefined Behavior)**이므로, 컴파일러 최적화에 따라 범위 검사 자체가 제거되는 등 예측하기 어려운 결과가 나올 수 있다.

### 3-4. 포인터 연산 오류

포인터를 잘못 증가·감소시키면 원래 객체의 유효한 메모리 범위를 벗어난 주소를 참조하게 될 수 있다.

- 포인터를 잘못된 크기만큼 증가시키는 경우
- 포인터의 시작 위치와 끝 위치를 잘못 계산하는 경우
- 포인터 연산 결과가 유효한 배열 범위를 벗어나는 경우
- 유효하지 않은 포인터를 역참조(Dereference)하는 경우

C 언어에서 배열의 마지막 원소 **바로 다음 위치(one-past-the-end)**를 가리키는 포인터를 계산하는 것은 허용되지만, 해당 포인터를 역참조하는 것은 허용되지 않는다. 또한 그보다 더 멀리 벗어난 위치로 포인터를 계산하는 것 자체도 표준상 미정의 동작이다.

→ 포인터 연산 시에는 주소가 계산되는지만이 아니라, 해당 주소가 **접근 가능한 객체의 범위에 포함되는지**도 고려해야 한다.

### 3-5. 반복문 종료 조건 오류

배열의 크기가 5인데 반복문이 0부터 5까지 실행되도록 설정하면 마지막 반복에서 유효하지 않은 인덱스에 접근하게 된다.

```c
int arr[5];
for (int i = 0; i <= 5; i++) {   // i < 5 이어야 함 (off-by-one)
    arr[i] = i;
}
```

- 반복문의 종료 조건을 잘못 설정한 경우
- 배열의 크기와 인덱스를 혼동한 경우
- 반복문 내부에서 인덱스가 예상보다 많이 증가하는 경우
- 데이터의 끝을 확인하는 조건이 누락된 경우

특히 `i <= length`와 `i < length`의 차이를 정확히 이해해야 한다.

## 4. 코드 예시와 ASan 탐지

### 4-1. OOB Read 예시

```c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[]) {
    int arr[5] = {10, 20, 30, 40, 50};
    int idx = argc > 1 ? atoi(argv[1]) : 0;

    // idx 범위 검증 없음 → OOB Read
    printf("arr[%d] = %d\n", idx, arr[idx]);
    return 0;
}
```

- `idx`는 사용자 입력이고 `0 <= idx < 5` 검증이 없다.
- `./read 2`는 정상(`30`)이지만, `./read 5`나 `./read -1`은 배열 밖의 값을 읽는다.

ASan으로 빌드하면 다음과 같이 탐지된다.

```bash
gcc -g -fsanitize=address -o read read.c
./read 5
```

```
==5387==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x6c1cd58d0034 at pc 0x63b4f397e4f9 ...
READ of size 4 at 0x6c1cd58d0034 thread T0
    #0 0x63b4f397e4f8 in main read.c:9
    ...
Address 0x6c1cd58d0034 is located in stack of thread T0 at offset 52 in frame
    #0 0x63b4f397e298 in main read.c:4

  This frame has 1 object(s):
    [32, 52) 'arr' (line 5) <== Memory access at offset 52 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow read.c:9 in main
```

- `READ of size 4`: 4바이트 **읽기** → OOB Read
- `[32, 52) 'arr'`: `arr`가 차지하는 범위(20바이트)인데, offset 52(= 범위의 끝 바로 다음)에 접근했다는 의미

### 4-2. OOB Write 예시

```c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[]) {
    int arr[5] = {10, 20, 30, 40, 50};
    int idx = argc > 1 ? atoi(argv[1]) : 0;
    int val = argc > 2 ? atoi(argv[2]) : 0;

    // idx 범위 검증 없음 → OOB Write
    arr[idx] = val;
    printf("arr[%d] = %d\n", idx, arr[idx]);
    return 0;
}
```

```bash
gcc -g -fsanitize=address -o write write.c
./write 5 1337
```

```
==5389==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x6ef7a68d0034 at pc 0x557c364e952a ...
WRITE of size 4 at 0x6ef7a68d0034 thread T0
    #0 0x557c364e9529 in main write.c:10
    ...
  This frame has 1 object(s):
    [32, 52) 'arr' (line 5) <== Memory access at offset 52 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow write.c:10 in main
```

- `WRITE of size 4`: 4바이트 **쓰기** → OOB Write
- 읽기/쓰기 구분은 ASan 출력의 첫 줄(`READ of` / `WRITE of`)로 판단할 수 있다.

※ ASan 없이 일반 빌드로 실행하면 인접한 스택 데이터를 읽고/덮어쓸 뿐 즉시 종료되지 않을 수 있다. 즉, **크래시가 나지 않는다고 안전한 것이 아니다.**

### 4-3. 수정 예시

```c
if (idx < 0 || idx >= 5) {      // 0 <= idx < N 검증
    fprintf(stderr, "invalid index\n");
    return 1;
}
```

## 5. OOB와 관련된 취약점 분류 (CWE)

OOB는 메모리 범위를 벗어난 접근이라는 공통적인 특징을 가지지만, 구체적인 접근 방식에 따라 여러 CWE(Common Weakness Enumeration)로 구분된다.

| CWE | 명칭 | 설명 |
| --- | --- | --- |
| CWE-119 | Improper Restriction of Operations within the Bounds of a Memory Buffer | 메모리 버퍼 범위 제한 실패 (상위 분류) |
| CWE-125 | Out-of-bounds Read | 범위를 벗어난 메모리 읽기 |
| CWE-126 | Buffer Over-read | 버퍼 **끝**을 넘어 읽기 (CWE-125의 하위) |
| CWE-127 | Buffer Under-read | 버퍼 **시작 이전**을 읽기 (CWE-125의 하위) |
| CWE-787 | Out-of-bounds Write | 범위를 벗어난 메모리 쓰기 |

```
CWE-119 (버퍼 범위 제한 실패)
 ├── CWE-125 (OOB Read)
 │     ├── CWE-126 (Buffer Over-read)
 │     └── CWE-127 (Buffer Under-read)
 └── CWE-787 (OOB Write)
```

- **CWE-119**: 매우 광범위한 상위 분류라서 MITRE에서는 취약점을 분류할 때 가능하면 더 구체적인 **CWE-125 / CWE-787**을 사용하도록 권장한다.
- **CWE-125**: 대표적인 영향은 민감 정보 노출과 서비스 거부이다.
- **CWE-787**: 대표적인 영향은 메모리 손상, 비정상 종료, 경우에 따른 비인가 코드 실행이다. 매년 CWE Top 25 상위권에 오르는 대표적인 취약점이다.

## 6. OOB의 보안상 영향

OOB는 단순한 프로그램 오류에 그치지 않고 보안의 3요소인 기밀성(Confidentiality), 무결성(Integrity), 가용성(Availability)에 영향을 미칠 수 있다.

### 6-1. 기밀성 침해 (Confidentiality)

OOB Read로 의도하지 않은 메모리 영역의 데이터를 읽을 수 있으며, 해당 메모리에 민감한 정보가 있으면 유출될 수 있다.

- 사용자 개인정보
- 인증 정보 및 세션 관련 데이터
- 암호화 키와 같은 중요 데이터
- 프로세스의 메모리 주소 (ASLR 우회에 활용 가능)
- 프로그램 내부 데이터

### 6-2. 무결성 침해 (Integrity)

OOB Write로 의도하지 않은 메모리 영역의 데이터를 변경할 수 있다. 인접한 변수나 중요한 데이터 구조가 손상될 수 있으며, 함수 포인터나 반환 주소 등 제어 흐름과 관련된 데이터가 손상될 수도 있다.

### 6-3. 가용성 침해 (Availability)

OOB Read와 Write 모두 접근 위반(Access Violation)이나 세그멘테이션 오류(Segmentation Fault)로 프로그램을 중단시킬 수 있다. 외부 입력으로 반복 유발할 수 있다면 서비스 거부(DoS) 공격으로 이어질 수 있다.

### 6-4. 임의 코드 실행 가능성

OOB 자체가 항상 임의 코드 실행을 의미하는 것은 아니다. 그러나 OOB Write로 제어 흐름 관련 메모리가 변경되거나 다른 취약점과 결합되는 경우 공격자가 의도한 코드 실행으로 이어질 수 있다. 실제 공격 가능성은 메모리 배치, 쓰기 가능한 범위, 입력값 제어 가능성, 실행 환경의 보호 기법 등에 따라 달라진다.

## 7. OOB와 다른 메모리 취약점의 차이

| 구분 | 핵심 문제 | 주요 특징 |
| --- | --- | --- |
| OOB | 메모리 객체의 유효 범위 초과 접근 | Read / Write 모두 가능 |
| Buffer Overflow | 버퍼 용량을 초과하는 데이터 기록 | 일반적으로 메모리 손상과 연관 |
| Stack Buffer Overflow | 스택 버퍼의 범위 초과 기록 | 스택 영역에서 발생 |
| Use-After-Free | 해제된 메모리 접근 | 메모리 수명 관리 오류 |

- **OOB vs Buffer Overflow**: Buffer Overflow는 버퍼 크기를 초과해 데이터를 **기록**하는 문제를 일반적으로 의미하고, OOB는 읽기·쓰기를 모두 포함하는 더 넓은 개념이다. 특히 OOB Read는 일반적인 의미의 Buffer Overflow와 구분된다. 대부분의 Buffer Overflow(스택 CWE-121, 힙 CWE-122)는 OOB Write(CWE-787)의 한 형태로 볼 수 있다.
- **OOB vs Stack Buffer Overflow**: Stack Buffer Overflow는 스택 영역에 한정되지만, OOB는 스택·힙·전역 데이터 영역 등 어디서든 발생할 수 있다. ([Week05 Stack Buffer Overflow](../../Week05/강은채/Stack-Buffer-Overflow.md) 참고)
- **OOB vs Use-After-Free(UAF)**: OOB는 객체의 **유효한 범위를 벗어난 위치**에 접근하는 문제이고, UAF는 이미 **수명이 끝난(해제된) 메모리**에 접근하는 문제이다. 원인은 다르지만 잘못된 포인터 사용과 메모리 관리 문제라는 공통점이 있다.

## 8. OOB 대응 방법

메모리에 접근하기 전 데이터의 크기, 인덱스, 포인터, 오프셋 등이 유효한 범위에 포함되는지 검증해야 한다.

### 8-1. 배열 인덱스 범위 검증

배열 크기가 N이면 `0 <= index < N` 조건을 만족하는 경우에만 접근한다. 특히 음수 인덱스 검증을 반드시 수행한다. (인덱스를 `size_t` 같은 부호 없는 타입으로 받으면 `index < N` 검사 하나로 음수까지 걸러지는 효과가 있다.)

### 8-2. 입력 데이터 길이 검증

파일, 네트워크 패킷, 사용자 입력 등 외부 데이터에 포함된 길이 정보는 신뢰하지 말고 실제 데이터 크기와 비교한다. 또한 프로그램이 허용하는 최대·최소 크기를 만족하는지도 확인한다.

### 8-3. 정수 연산 검증

메모리 크기나 오프셋을 계산할 때 정수 오버플로우/언더플로우가 없는지 검증한다.

- 배열 원소 개수와 원소 크기의 곱셈
- 버퍼의 시작 주소와 오프셋의 덧셈
- 전체 데이터 길이에서 현재 위치를 빼는 연산
- 외부 입력값을 이용한 메모리 크기 계산

### 8-4. 포인터 및 메모리 접근 검증

포인터 연산으로 계산된 주소가 유효한 객체의 범위에 포함되는지, 접근하려는 데이터 크기가 남아 있는 메모리 범위를 초과하지 않는지 확인한다. 포인터가 가리키는 메모리의 수명과 유효성도 함께 고려한다.

### 8-5. 안전한 라이브러리 및 언어 기능 활용

C++에서는 `std::array`, `std::vector` 등의 컨테이너를 활용할 수 있다.

- `operator[]`는 **범위 검사를 하지 않는다.** (범위를 벗어나면 미정의 동작)
- `.at()`은 범위를 벗어나면 `std::out_of_range` 예외를 던진다.
- 안전한 컨테이너를 쓰더라도 포인터를 통한 직접 접근이나 잘못된 길이 계산이 있으면 메모리 오류가 발생할 수 있다.

### 8-6. 메모리 오류 탐지 도구 활용

| 도구 | 설명 |
| --- | --- |
| AddressSanitizer (ASan) | 메모리 접근 오류를 탐지하는 컴파일러 기반 도구 (`-fsanitize=address`) |
| Valgrind | 메모리 접근 및 메모리 관리 오류를 분석하는 도구 |
| Static Analysis | 소스코드 분석을 통해 잠재적인 메모리 오류를 탐지 |
| Fuzzing | 다양한 입력값을 전달하여 비정상적인 메모리 접근을 유발하고 탐지 |

## 9. 핵심 정리

> OOB(Out-of-Bounds)는 프로그램이 할당된 메모리 객체의 유효한 범위를 벗어나 메모리에 접근하면서 발생하는 취약점이다.
>
> OOB Read는 범위를 벗어난 메모리에서 데이터를 읽는 문제(CWE-125)이며, OOB Write는 범위를 벗어난 위치에 데이터를 기록하는 문제(CWE-787)이다.
>
> 배열 인덱스 검증 누락, 입력 데이터 길이 검증 실패, 정수 오버플로우/언더플로우, 포인터 연산 오류 등으로 발생하며, 정보 노출·메모리 손상·비정상 종료를 유발하고 다른 취약점과 결합되어 더 큰 위협이 될 수 있다.
>
> **핵심은 프로그램이 의도한 메모리 영역 안에서만 데이터를 읽고 쓸 수 있도록 보장하는 것이다.**
