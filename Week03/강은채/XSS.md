# XSS (Cross-Site Scripting)

## 1. 개념

**XSS(Cross-Site Scripting)** 는 신뢰할 수 없는 데이터가 웹 페이지에서 **HTML이나 JavaScript 코드로 해석·실행**될 수 있는 취약점이다.
공격자는 이를 이용해 페이지를 열람하는 **사용자의 브라우저에서 피해자 권한으로 동작하는 스크립트**를 실행시킬 수 있다.

- 공격 대상은 다른 일반 사용자일 수도 있고, **관리자가 보는 게시판에 저장형 XSS를 심는 경우**처럼 특정 권한을 가진 사용자를 노릴 수도 있다.
- 서버가 아니라 **피해자의 브라우저**에서 코드가 실행된다는 점이 핵심이다.
- **이름 유래**: Cross-Site Scripting은 원래 CSS로 줄일 수 있지만, CSS(Cascading Style Sheets)와 혼동돼서 **XSS**로 표기한다.

- **OWASP Top 10 (2021) 분류**: A03:2021 - Injection
- **영향**: 아래 '5. XSS 공격의 영향' 참고 (쿠키 탈취뿐 아니라 피해자 권한으로 하는 모든 행동)

## 2. 발생 원리

XSS는 **신뢰할 수 없는 데이터가 적절한 처리 없이 실행 가능한 문맥(HTML, JavaScript 등)에 삽입되어, 브라우저에서 코드로 해석·실행될 때** 발생한다. 입력이 "데이터"가 아니라 "코드"로 해석되는 것이 문제다.

핵심은 "사용자 입력" 자체가 아니라 **그 입력이 코드로 해석되는 위치에 들어가는 것**이다.
같은 `<script>alert(1)</script>` 라도,
- `<p>&lt;script&gt;...&lt;/p>` 처럼 **문자로 출력되면** 실행되지 않고,
- `<p><script>...</script></p>` 처럼 **HTML로 해석되면** 실행된다.

유형에 따라 발생 지점이 다르다.
- **Stored / Reflected** → 주로 **서버가 입력값을 응답에 포함**시키는 과정에서 발생
- **DOM-based** → 서버 응답과 무관하게, **클라이언트 JavaScript가 입력값을 위험한 DOM에 넣는** 과정에서 발생

### Source → Sink (특히 DOM XSS 분석에 유용)

- **Source**: 공격자가 제어할 수 있는 입력이 들어오는 지점 (예: `location.search`, `location.hash`, `document.referrer`)
- **Sink**: 그 데이터가 코드로 해석·실행될 수 있는 지점 (예: `innerHTML`, `document.write()`, `eval()`)

```
location.hash  →  input  →  element.innerHTML  →  HTML로 해석  →  XSS
   (Source)                      (Sink)
```

취약점 분석은 결국 **"Source에서 온 값이 인코딩 없이 Sink에 도달하는 경로"** 를 찾는 일이다.

### 취약한 코드 예시

```php
<?php
// 검색어를 그대로 화면에 출력 → 취약
$q = $_GET['q'];
echo "검색 결과: " . $q;
?>
```
```
정상 입력: ?q=hello  →  검색 결과: hello
공격 입력: ?q=<script>...</script>  →  브라우저가 <script>를 코드로 해석해 실행
```

## 3. XSS 유형

| 유형 | 발생 과정 | 대표 예 |
|------|-----------|---------|
| **Stored (저장형)** | 악성 입력이 서버/DB에 **저장**된 뒤, 그 데이터를 **열람하는 사용자**의 브라우저에서 실행 | 게시글, 댓글 |
| **Reflected (반사형)** | 요청에 담긴 입력이 서버 응답에 **즉시 반영**되어 실행 (주로 조작된 링크 클릭 유도) | 검색어, URL 파라미터 |
| **DOM-based** | 클라이언트 JS가 입력값을 **위험한 DOM 처리**에 사용해 실행 (서버 응답에 반영 안 돼도 발생) | `innerHTML`, `document.write()` |

> 참고: Stored/Reflected는 "입력이 **서버를 어떻게 거치는가**" 기준이고,
> DOM-based는 "**클라이언트 DOM 처리**에서 발생하는가" 기준이라, 완전히 같은 축의 분류는 아니다.

## 4. XSS 발생 맥락 (출력 문맥)

같은 입력이라도 **어느 위치에 출력되는지**에 따라 필요한 방어(인코딩)가 달라진다.
"`<`, `>` 만 바꾸면 된다"는 접근으로는 충분하지 않다.

| 출력 위치 | 예시 | 필요한 처리 |
|-----------|------|-------------|
| HTML 본문 | `<div>입력</div>` | HTML 엔티티 인코딩 (`<`→`&lt;` 등) |
| HTML 속성 | `<input value="입력">` | 속성 문맥에 맞는 인코딩 |
| JavaScript | `<script>var x='입력';</script>` | JS 문자열 이스케이프 (HTML 인코딩만으론 부족) |
| URL | `<a href="입력">` | 허용할 URL scheme/형식 검증 + 문맥에 맞는 인코딩 |

## 5. XSS 공격의 영향

XSS의 피해를 "쿠키 탈취"로만 생각하면 안 된다. 핵심은 **피해자 브라우저에서 피해자 권한으로
임의의 JavaScript가 실행된다**는 점이며, 그 결과 다음이 가능하다.

- **정보 탈취**: JavaScript로 접근 가능한 쿠키·페이지 내 민감 정보 유출
  - 단, **`HttpOnly`가 설정된 쿠키는 `document.cookie`로 읽을 수 없다.**
    쿠키 탈취 가능 여부는 쿠키 설정과 실행 페이지의 권한에 따라 달라지고,
    그 쿠키가 인증용 세션 쿠키라면 세션 탈취로 이어질 수 있다.
- **화면 변조 / 피싱**: 가짜 로그인 폼을 삽입해 계정 정보 입력 유도
- **인증된 요청 수행**: 피해자 권한으로 비밀번호 변경·게시글 작성 등 실행
  - XSS는 이미 피해자 브라우저에서 실행되므로, **CSRF 토큰이 있어도 우회**해 인증된 요청을 보낼 수 있다.
- **사용자 입력 탈취**: 키 입력 기록 등

## 6. 대표 취약 코드

### 6-1. 서버 측 출력 (Stored/Reflected)
입력값을 이스케이프 없이 응답 HTML에 넣는 경우 ('2. 발생 원리' 예시 참고).

### 6-2. DOM XSS — `innerHTML` vs `textContent`
```js
// 취약: 문자열을 HTML로 해석 -> <script> 등이 실행될 수 있음
element.innerHTML = userInput;

// 안전: 문자열을 텍스트로만 삽입 -> 코드로 해석되지 않음
element.textContent = userInput;
```
- `innerHTML`, `outerHTML`, `document.write()` 등 HTML을 해석하는 API는
  신뢰할 수 없는 데이터를 전달할 경우 XSS가 발생할 수 있으므로 주의.
- 단, `textContent`가 만능은 아니다. **HTML을 의도적으로 허용해야 하는 기능**이라면
  별도의 안전한 HTML 정제(sanitize)가 필요하다.

## 7. XSS 방어

1. **출력 시 문맥에 맞는 인코딩** ★ 가장 기본
   - HTML 본문/속성/JS/URL 등 **출력 위치에 맞는** 인코딩을 적용 ('4. XSS 발생 맥락' 참고).
   - 대부분의 템플릿 엔진은 자동 이스케이프를 제공 → 이 기능을 끄지 않는다.
2. **안전한 DOM API 사용**
   - `textContent` 등을 우선 사용하고, `innerHTML`/`document.write()`/`eval()` 은 지양.
3. **입력값 검증 (보조)**
   - 허용 형식만 통과시키되, **입력 검증만으로 XSS를 막을 수는 없다.**
     정상적으로 보이는 값도 출력 위치에서 코드가 될 수 있으므로 출력 시 처리가 핵심.
4. **CSP(Content-Security-Policy)**
   - 스크립트 실행 출처를 제한해 **피해를 줄이는 방어 계층**. 설정이 느슨하면 우회 가능.
     출력 인코딩을 대체하는 게 아니라 추가 방어책.
5. **쿠키 보안 속성 (피해 완화)**
   - `HttpOnly`(JS의 쿠키 접근 차단), `Secure`(HTTPS 전송), `SameSite`(교차 사이트 전송 제한).
   - XSS 자체를 막지는 않고, 쿠키 탈취 등 **피해를 줄이는** 보조 수단.

## 8. XSS와 CSRF의 관계

| 구분 | XSS | CSRF |
|------|-----|------|
| 핵심 | 공격자 스크립트가 피해자 브라우저에서 **실행** | 피해자의 인증 정보로 **요청을 위조 전송** |
| 조건 | 코드가 브라우저에서 실행될 수 있어야 함 | 피해자가 **로그인된 상태**여야 함 |
| 응답 확인 | 실행된 JavaScript가 조건을 충족하면 응답 데이터에 접근 가능 | 일반적으로 공격자가 응답 내용을 직접 읽을 수 없음 |
| 대표 방어 | 출력 인코딩, 안전한 DOM 처리, CSP | CSRF 토큰, SameSite |

> XSS가 발생하면 피해자 브라우저에서 임의 JS를 실행할 수 있어,
> **CSRF 방어가 있어도 인증된 요청을 수행하는 방식으로 우회**할 수 있다.

## 9. 핵심 정리

1. **XSS의 본질** — 신뢰할 수 없는 데이터가 브라우저에서 **코드로 해석·실행**되는 것.
2. **유형** — 입력이 어디서 처리·실행되는지에 따라 Stored / Reflected / DOM-based.
3. **Source → Sink** — 사용자 제어 데이터가 위험한 실행 지점에 도달하는 흐름을 추적.
4. **방어의 핵심** — **출력 문맥에 맞는 인코딩 + 안전한 API 사용** (입력 검증·CSP·쿠키 속성은 보조).
