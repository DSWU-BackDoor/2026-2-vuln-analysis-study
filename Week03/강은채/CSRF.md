# CSRF (Cross-Site Request Forgery)

## 1. 개념

**CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)** 는 **로그인된 사용자의 인증 상태를 악용**하여, 사용자가 의도하지 않은 요청을 서버에 보내도록 만드는 공격이다.

피해자가 이미 로그인된 상태에서 공격자가 만든 페이지·링크를 열면,
피해자의 브라우저가 **해당 사이트의 인증 쿠키 등을 자동으로 요청에 포함**하는 특성을 악용한다.

- **OWASP Top 10 (2021)**: A01 - Broken Access Control과 관련된 공격으로 볼 수 있음
- **영향**: 비밀번호·이메일 변경, 송금, 게시글 작성 등 **피해자 권한으로 상태를 바꾸는 행위**
  (서버의 상태를 변경하는 요청이 주요 대상이며, 비밀번호·이메일 변경, 게시글 작성, 송금 등의 행위가 대표적인 예.)

## 2. XSS와의 차이 (자주 헷갈림)

| 구분 | XSS | CSRF |
|------|-----|------|
| 핵심 | 공격자의 스크립트를 피해자 브라우저에서 실행 | 피해자의 인증 상태를 이용해 요청 발생 |
| 필요 조건 | 공격자가 스크립트를 실행시킬 수 있는 XSS 취약점 | 피해자가 인증된 상태 + 공격자가 요청을 유도할 수 있어야 함 |
| 공격자가 얻는 것 | 실행된 스크립트의 권한에 따라 데이터 접근·행동 가능 | 일반적으로 피해자의 인증 정보 자체를 얻는 것은 아님 |
| 한 줄 요약 | 코드를 실행시킨다 | 요청을 대신 보내게 만든다 |

> XSS가 성공하면 공격자의 JavaScript가 피해자 브라우저 권한으로 실행되므로,
> CSRF 토큰이 포함된 정상 요청을 대신 만들어 **CSRF 방어를 우회할 가능성**이 있다.
> 즉 XSS는 CSRF보다 공격 범위가 넓어질 수 있다.

## 3. 발생 원리

서버가 요청을 처리할 때 **"이 요청이 우리 사이트에서 사용자가 직접 의도해 보낸 것인지"** 를
확인하지 않고, **쿠키만으로 인증**하면 발생한다.

### CSRF가 성립하기 위한 조건

일반적으로 다음 조건이 모두 필요하다.

1. 피해자가 대상 사이트에 **로그인(인증)된 상태**여야 한다.
2. 공격자가 피해자의 브라우저에서 **대상 사이트로 요청을 발생**시킬 수 있어야 한다.
3. 서버가 그 요청을 **정상적인 요청으로 받아들여야** 한다. (별도 검증이 없음)
4. 그 요청이 피해자의 **상태를 변경**할 수 있어야 한다. (송금, 정보 변경 등)

### 공격 예시

피해자가 어떤 은행 사이트에 로그인된 상태라고 하자.
공격자는 아래 같은 페이지를 만들어 피해자가 열게 유도한다.

```html
<!-- 공격자 페이지: 피해자가 열기만 해도 자동 전송 -->
<img src="https://bank.example/transfer?to=attacker&amount=1000000">
```

- 피해자 브라우저는 `bank.example` 로 요청을 보내면서 **로그인 쿠키를 자동으로 첨부**한다.
- 서버는 쿠키가 유효하니 정상 요청으로 보고 **송금을 처리**한다.
- 피해자는 이미지를 불러온 줄 알지만 실제로는 송금이 일어난 것.

POST 요청도 자동 제출되는 폼(form)으로 동일하게 위조할 수 있다.

```html
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000000">
</form>
<script>document.forms[0].submit();</script>
```

## 4. 방어 방법

1. **CSRF 토큰** ★ 핵심 방어
   - 서버가 폼마다 **예측 불가능한 토큰**을 심고, 요청 시 그 값을 함께 검증
   - 동작 과정:
     ```
     ① 사용자가 정상 폼 요청
           ↓
     ② 서버가 랜덤 CSRF 토큰 발급
           ↓
     ③ 정상 폼에 토큰 포함
           ↓
     ④ 사용자가 요청 전송 (쿠키 + 토큰)
           ↓
     ⑤ 서버가 쿠키 + 토큰 검증
           → 일치: 요청 처리 / 불일치: 요청 거부
     ```
   - 공격자 사이트에서는 유효한 토큰을 알 수 없어 위조 요청이 거부된다.
     단, **XSS가 있으면** 정상 페이지에서 토큰을 읽어 우회할 수 있다.
2. **SameSite 쿠키 속성** — `SameSite` 쿠키 속성을 적절하게 설정하면 교차 사이트 요청에서 인증 쿠키의 전송을 제한하여 CSRF를 완화할 수 있다. `Strict`가 더 엄격하고, `Lax`는 일부 교차 사이트 탐색에서 쿠키가 전송될 수 있다.
3. **Origin / Referer 헤더 검증** — 요청의 `Origin` 또는 `Referer`를 확인하여 신뢰할 수 있는 출처에서 발생한 요청인지 검증한다.
4. **중요한 작업에 재인증** — 비밀번호 변경·송금 시 비밀번호를 다시 확인
5. **상태 변경은 GET으로 처리하지 않기** — GET은 링크·이미지 등으로 쉽게 요청될 수 있으므로 상태 변경에 사용하지 않는다. 단, **POST를 사용하더라도 CSRF 토큰 등의 별도 방어가 필요하다.**

## 5. 핵심 정리

> CSRF는 "브라우저가 쿠키를 자동으로 붙여 보낸다"는 점을 악용해,
> 로그인된 피해자 권한으로 **원치 않는 상태 변경 요청**을 일으키는 공격이다.
> **CSRF 토큰 + SameSite 쿠키**가 핵심 대책이다.
