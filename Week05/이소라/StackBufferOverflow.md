# 시스템 취약점 분석 스터디 노트 — Stack Buffer Overflow

> CWE-121 (Stack-based Buffer Overflow)에 해당하며, CWE Top 25에서 상위권에 꾸준히 오르는 **메모리 손상(Memory Corruption)** 취약점의 대표 주자다.

---

## 1. 개념

**스택에 할당된 버퍼에 그 크기보다 큰 데이터를 써서, 인접한 메모리를 덮어쓰는 것이다.**

- **버퍼(Buffer)** 는 데이터를 임시로 담는 고정 크기의 메모리 공간이다 (예: `char buf[16]`).
- **스택(Stack)** 은 함수 호출 시 지역 변수, 저장된 프레임 포인터, **리턴 주소** 등이 쌓이는 메모리 영역이다.

> 핵심은 "경계 검사(Bounds Check)가 없다"는 것이다. C/C++은 배열 길이를 자동으로 검사하지 않으므로, 개발자가 직접 확인하지 않으면 넘친 데이터가 그대로 옆 메모리를 덮는다.

**Stack Buffer Overflow** 는 이렇게 넘친 데이터가 **리턴 주소 같은 제어 데이터**를 덮어, 프로그램의 실행 흐름이 공격자 의도대로 바뀔 수 있는 상태를 말한다.

---

## 2. 핵심 구조 — 스택 프레임

함수가 호출되면 스택에 다음 순서로 데이터가 쌓인다 (x86 기준, 스택은 **높은 주소 → 낮은 주소**로 자란다).

```
높은 주소
┌──────────────────────┐
│ 함수 인자 (args)      │
├──────────────────────┤
│ 리턴 주소 (RET)       │  ← 함수가 끝나면 돌아갈 위치
├──────────────────────┤
│ 저장된 EBP/RBP (SFP)  │  ← 이전 함수의 프레임 포인터
├──────────────────────┤
│ 지역 변수 buf[16]     │  ← 여기서부터 쓰기 시작해 위로 넘친다
└──────────────────────┘
낮은 주소
```

| 요소                      | 설명                                                                            |
| ------------------------- | ------------------------------------------------------------------------------- |
| 지역 변수 (버퍼)          | 함수 안에서 선언한 배열이다. 쓰기는 **낮은 주소 → 높은 주소** 방향으로 진행된다 |
| SFP (Saved Frame Pointer) | 호출한 함수의 스택 프레임 기준점이다                                            |
| RET (Return Address)      | 함수 종료(`ret`) 시 CPU가 점프할 주소다. **공격의 핵심 표적이다**               |

> 버퍼는 위쪽으로 쓰이고, 그 위에 SFP와 RET가 있다. 그래서 버퍼가 넘치면 **SFP → RET 순서로 덮인다.**

---

## 3. 발생 원인 — 위험한 함수

길이를 검사하지 않는 C 표준 함수들이 주원인이다.

| 위험 함수                | 문제점                                          | 대안                                   |
| ------------------------ | ----------------------------------------------- | -------------------------------------- |
| `gets()`                 | 입력 길이를 전혀 제한하지 않는다 (C11에서 삭제) | `fgets(buf, sizeof(buf), stdin)`       |
| `strcpy()`               | 원본이 대상보다 길어도 그냥 복사한다            | `strncpy()`, `strlcpy()`, `strcpy_s()` |
| `strcat()`               | 이어붙일 때 남은 공간을 확인하지 않는다         | `strncat()`, `strlcat()`               |
| `sprintf()`              | 출력 길이를 제한하지 않는다                     | `snprintf()`                           |
| `scanf("%s")`            | 폭(width) 지정이 없으면 무제한으로 읽는다       | `scanf("%15s", buf)`                   |
| `memcpy()` (잘못된 길이) | 길이 인자를 사용자 입력에서 그대로 받는다       | 길이를 대상 크기와 비교한 후 복사한다  |

### 취약한 코드 예시

```c
void greet(char *input) {
    char name[16];
    strcpy(name, input);   // input이 16바이트를 넘으면 SFP, RET까지 덮인다
    printf("Hello, %s\n", name);
}
```

### 안전한 코드 예시

```c
void greet(const char *input) {
    char name[16];
    snprintf(name, sizeof(name), "%s", input);   // 최대 15자 + '\0'만 쓴다
    printf("Hello, %s\n", name);
}
```

## 4. 대표 공격 유형

### (1) 리턴 주소 덮어쓰기 (Classic / Return Address Overwrite)

버퍼를 넘치게 해 RET를 원하는 주소로 바꾼다. 함수가 `ret`할 때 그 주소로 실행 흐름이 넘어간다.

```
[ buf 채우기 ][ SFP 덮기 ][ RET → 공격자가 정한 주소 ]
```

> 가장 기본 형태다. 시험에서는 "버퍼 → SFP → RET 순서로 덮인다"와 "RET를 바꿔 실행 흐름을 탈취한다"가 단골로 나온다.

### (2) 쉘코드 주입 (Shellcode Injection)

버퍼 안에 실행할 기계어(쉘코드)를 넣고, RET를 그 버퍼 주소로 돌린다.
주소를 정확히 몰라도 맞추기 쉽게 **NOP Sled**(아무것도 안 하는 명령어 `0x90`을 길게 깐 구간)를 앞에 둔다.

> **NX/DEP**가 켜져 있으면 스택에서 코드 실행이 막히므로 이 방식은 실패한다.

### (3) Return-to-libc (RTL)

스택에 코드를 넣는 대신, 이미 메모리에 있는 라이브러리 함수(예: `system()`)로 RET를 돌린다.
NX/DEP를 우회하기 위해 등장한 기법이다.

### (4) ROP (Return-Oriented Programming)

기존 코드 조각 중 `ret`으로 끝나는 짧은 명령어 묶음(**가젯, Gadget**)을 이어붙여 원하는 동작을 만든다.
RTL을 일반화한 형태이며, 현대 익스플로잇의 표준 기법이다.

### (5) 지역 변수 / 함수 포인터 덮어쓰기

RET까지 가지 않아도, 버퍼 바로 위의 **다른 지역 변수**(예: `is_admin` 플래그, 함수 포인터)를 바꿔 로직을 우회할 수 있다.

```c
int is_admin = 0;
char buf[8];
gets(buf);           // buf가 넘쳐 is_admin을 0이 아닌 값으로 덮을 수 있다
if (is_admin) { ... }
```

### (6) Off-by-One

경계 검사를 **딱 1바이트** 잘못해서 생긴다 (`<=` vs `<`, 널 종료 문자 `'\0'` 누락).
1바이트만 넘쳐도 SFP의 최하위 바이트를 바꿔 실행 흐름에 영향을 줄 수 있다.

```c
for (i = 0; i <= 16; i++) buf[i] = input[i];   // buf[16]은 범위 밖이다
```

## 5. 꼭 알아야 할 포인트

- **스택은 아래로 자라고, 버퍼는 위로 쓰인다.** 그래서 넘친 데이터가 SFP와 RET를 덮는다.
- **Stack vs Heap Overflow를 구분한다.** 스택은 RET 같은 제어 데이터를, 힙은 청크 메타데이터나 객체 포인터를 덮는다 (Heap은 CWE-122다).
- **보호 기법은 하나만으로 완벽하지 않다.** 실제로는 여러 개를 겹쳐 쓴다 (Defense in Depth).

| 보호 기법              | 원리                                                                | 막는 것                    | 우회 개념                    |
| ---------------------- | ------------------------------------------------------------------- | -------------------------- | ---------------------------- |
| **Stack Canary** (SSP) | 버퍼와 SFP 사이에 랜덤 값을 두고, 함수 종료 전 바뀌었는지 검사한다  | 연속적인 RET 덮어쓰기      | 카나리 값 유출(Leak)         |
| **NX / DEP**           | 스택·힙 영역을 실행 불가로 설정한다                                 | 스택 쉘코드 실행           | RTL, ROP                     |
| **ASLR**               | 스택·힙·라이브러리 주소를 실행마다 무작위로 배치한다                | 고정 주소에 의존한 공격    | 주소 유출, 브루트포스(32bit) |
| **PIE**                | 실행 파일 자체의 코드 주소까지 무작위화한다                         | 바이너리 내 가젯 고정 주소 | 코드 주소 유출               |
| **RELRO**              | GOT 등 재배치 영역을 읽기 전용으로 만든다                           | GOT 덮어쓰기               | Partial RELRO의 남은 영역    |
| **CFI / Shadow Stack** | 리턴 주소를 별도 보호된 스택에 복사해 두고 비교한다 (예: Intel CET) | ROP 등 흐름 변조           | 아직 우회가 어렵다           |

> 시험 단골 질문: "카나리는 어디에 위치하는가?" → **버퍼와 SFP(+RET) 사이**다. "NX를 우회하는 기법은?" → **RTL, ROP**다.

- **언어 선택도 방어다.** Java, Python, Go, Rust 같은 메모리 안전(Memory-Safe) 언어는 경계 검사를 자동으로 하므로 이 취약점이 원천적으로 거의 발생하지 않는다.

## 6. 방어 (Mitigation)

1. **위험 함수를 쓰지 않는다.** `gets`, `strcpy`, `sprintf` 등은 길이 제한 버전(`fgets`, `snprintf`, `strlcpy`)으로 교체한다.
2. **모든 입력의 길이를 검증한다.** 복사·연결 전에 대상 버퍼 크기(`sizeof`)와 비교하고, 널 종료 문자 공간까지 계산한다.
3. **컴파일러 보호 옵션을 켠다.**
   ```bash
   # GCC 예시
   gcc -fstack-protector-strong -D_FORTIFY_SOURCE=2 -O2 \
       -fPIE -pie -Wl,-z,relro,-z,now -Wl,-z,noexecstack app.c
   ```
4. **OS 수준 보호를 유지한다.** ASLR, NX/DEP를 끄지 않는다 (`/proc/sys/kernel/randomize_va_space = 2`).
5. **정적 분석과 퍼징을 수행한다.** 정적 분석(SAST)으로 위험 함수를 찾고, 퍼저(AFL++, libFuzzer)와 **AddressSanitizer(`-fsanitize=address`)** 로 런타임 오버플로를 잡는다.
6. **메모리 안전 언어를 우선 검토한다.** 신규 개발이나 고위험 모듈(파서, 네트워크 처리)은 Rust 등으로 작성하는 것을 고려한다.
7. **최소 권한으로 실행한다.** 오버플로가 터져도 피해 범위가 줄도록 서비스 계정 권한을 제한하고 샌드박스를 적용한다.
8. **보안 패치를 신속히 적용한다.** 라이브러리와 OS의 알려진 오버플로 취약점(CVE)을 지속적으로 추적한다.
