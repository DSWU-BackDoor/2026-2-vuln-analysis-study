# Stack Buffer Overflow (스택 버퍼 오버플로우)

## 1. 개념

**버퍼 오버플로우(Buffer Overflow)**는 프로그램이 버퍼(고정 크기의 메모리 공간)에 할당된 크기보다 많은 데이터를 기록할 때, 데이터가 버퍼의 경계를 넘어 인접한 메모리 영역을 덮어쓰는 취약점이다.

그중 **스택 버퍼 오버플로우(Stack Buffer Overflow)**는 스택(Stack)에 할당된 지역 변수 등의 버퍼에 크기를 초과하는 데이터가 기록되어, 같은 스택 프레임의 다른 데이터까지 손상시키는 취약점이다.

- **분류**: CWE-121 (Stack-based Buffer Overflow), 메모리 손상(Memory Corruption) 계열
- **영향**: 프로그램 비정상 종료, 메모리 데이터 손상, 실행 흐름 탈취 및 임의 코드 실행 등
    - 실제 영향 범위는 덮어쓸 수 있는 데이터와 적용된 보호 기법에 따라 달라진다.
- **발생 환경**: 주로 C/C++처럼 메모리 경계 검사를 자동으로 수행하지 않는 언어에서 발생한다.

## 2. 배경

### 2-1. 스택 메모리 구조

- **스택(Stack)**은 함수가 호출될 때마다 해당 함수의 실행에 필요한 정보가 저장되는 메모리 영역이다.
- 함수 호출 시 생성되는 메모리 영역을 **스택 프레임(Stack Frame)**이라고 한다.
- 일반적인 x86/x86-64 환경에서는 함수가 호출될 때 스택이 높은 메모리 주소에서 낮은 메모리 주소 방향으로 확장된다.
- 반면 버퍼에 데이터를 연속적으로 기록할 때는 낮은 메모리 주소에서 높은 메모리 주소 방향으로 진행된다.

따라서 일반적인 스택 프레임 배치에서는 버퍼에 크기를 초과하는 데이터를 입력하면 높은 주소에 위치한 SFP(Saved Frame Pointer)나 반환 주소 등의 데이터까지 덮어쓸 수 있다.

일반적인 x86-64 스택 프레임 구조 예시는 아래와 같다.

```
          [ 높은 주소 ]
   ┌─────────────────────────┐
   │   이전 함수의 프레임 ...   │
   ├─────────────────────────┤
   │   Return Address (RET)  │  ← 함수가 끝나고 돌아갈 주소
   ├─────────────────────────┤
   │   Saved Frame Pointer   │  ← 이전 함수의 프레임 포인터
   │         (SFP)           │
   ├─────────────────────────┤
   │   지역 변수 / buffer[]    │  ← 입력 데이터가 저장되는 공간
   └─────────────────────────┘
          [ 낮은 주소 ]
                │
                │ 버퍼에 데이터 기록
                ▼
       낮은 주소 → 높은 주소
```

※ 실제 스택 프레임의 메모리 배치는 컴파일러, 아키텍처, 컴파일 옵션 및 함수 호출 규약 등에 따라 달라질 수 있다. SFP가 생략되거나 다른 데이터가 배치될 수도 있다.

### 2-2. 반환 주소(Return Address)가 핵심인 이유

- 함수가 호출되면 CPU는 함수 실행이 끝난 후 돌아갈 명령어의 주소를 반환 주소(Return Address)로 저장한다.
- 함수 실행이 종료되면 `ret` 명령어를 통해 저장된 반환 주소로 돌아가 실행을 이어간다.
- 따라서 스택 버퍼 오버플로우를 통해 반환 주소를 공격자가 원하는 주소로 덮어쓸 수 있다면, 함수 종료 시 원래 실행 흐름이 아닌 다른 위치에서 명령어가 실행되도록 만들 수 있다.

→ 스택 버퍼 오버플로우를 이용해 **프로그램의 실행 흐름을 탈취하는 원리** 

## 3. 발생 원리

스택 버퍼 오버플로우는 주로 입력 데이터의 길이를 제대로 검사하지 않고, 고정 크기 버퍼에 데이터를 복사하거나 기록할 때 발생한다.

### 위험한 함수 (경계 검사 미흡)

| 함수 | 문제점 |
| --- | --- |
| `gets(buf)` | 입력 길이를 제한하지 않음. C11부터 표준 라이브러리에서 제거된 함수 |
| `strcpy(dst, src)` | 원본 문자열의 길이만큼 복사하며 목적지 버퍼의 크기를 확인하지 않음 |
| `scanf("%s", buf)` | 공백 전까지 입력받으며 입력 길이를 제한하지 않으면 버퍼를 초과할 수 있음 |
| `sprintf(dst, ...)` | 출력 결과가 목적지 버퍼의 크기를 초과할 수 있음 |
| `strcat(dst, src)` | 기존 문자열 뒤에 추가할 공간이 충분한지 확인하지 않음 |

### 취약한 코드 예시

```c
#include <stdio.h>

void vuln() {
    char buf[64];  // 64바이트 버퍼
    gets(buf);     // 입력 길이 제한 없이 데이터 저장 → 취약
}

int main() {
    vuln();
    return 0;
}
```

- `buf`는 64바이트 크기로 할당되어 있다.
- 하지만 `gets()`는 입력 데이터의 길이를 제한하지 않고 버퍼에 기록한다.
- 따라서 64바이트를 초과하는 입력이 들어오면 버퍼의 경계를 넘어 인접 메모리 영역을 덮어쓸 수 있다.
- 이 과정에서 스택 프레임에 저장된 다른 데이터나 반환 주소 등이 손상될 수 있다.

※ `gets()`는 입력 문자열 끝에 널 종료 문자(`\0`)도 기록하므로, 입력 데이터가 버퍼 크기에 도달하거나 초과하면 널 종료 문자에 의해서도 버퍼 경계를 벗어난 쓰기가 발생할 수 있다.

## 4. 공격 원리

### 4-1. 오프셋(Offset) 계산

**오프셋(Offset)**은 버퍼의 시작 주소부터 반환 주소(RET)까지의 거리를 의미한다.

반환 주소를 덮어쓰려면 버퍼의 시작 위치부터 반환 주소까지 몇 바이트를 채워야 하는지 알아야 한다.

**64비트 환경에서의 가상 예시**

```
[ buf (64) ][ SFP (8) ][ RET (8) ]
 └── 64 ──┘ └── 8 ──┘

버퍼 시작부터 RET까지의 거리
= buf(64) + SFP(8)
= 72바이트
```

- 위와 같은 메모리 배치라면 버퍼 시작부터 72바이트를 채운 뒤, 다음 데이터부터 반환 주소를 덮어쓸 수 있다.
- 64비트 환경에서 SFP와 반환 주소가 각각 8바이트라는 가정. 실제 오프셋은 컴파일러와 메모리 배치 등에 따라 달라지므로, 항상 72바이트인 것은 아니다.

**오프셋을 찾는 방법**

- `AAAA...`와 같은 반복 문자를 입력해 프로그램이 비정상 종료되는지 확인한다.
- `cyclic` 패턴을 이용해 반환 주소가 덮인 위치를 정확하게 계산할 수 있다.
- 디버거(GDB 등)를 통해 레지스터와 스택의 상태를 확인하여 실제 오프셋을 파악한다.

### 4-2. RET를 어디로 덮느냐 (대표적인 공격 기법)

반환 주소를 덮어쓸 수 있다면 공격자는 해당 주소를 조작하여 프로그램의 실행 흐름을 변경할 수 있다.

**① ret2win / 특정 함수 호출**

- 프로그램 내부에 이미 존재하는 특정 함수의 주소로 반환 주소를 덮어쓰는 방식이다.
- 예를 들어 바이너리 내부에 플래그를 출력하는 함수가 있다면 해당 함수로 실행 흐름을 이동시킬 수 있다.
- 특정 함수뿐 아니라 `system()` 등의 라이브러리 함수를 이용하는 공격도 가능하다.

**② 셸코드(Shellcode) 실행**

- 공격자가 실행하고자 하는 기계어 코드인 셸코드를 버퍼에 삽입한다.
- 반환 주소를 해당 셸코드가 위치한 메모리 주소로 변경하여 실행을 유도한다.
- 단, NX가 적용되지 않아 해당 메모리 영역에서 명령어 실행이 가능한 경우에 주로 사용된다.

**③ ROP(Return-Oriented Programming)**

- NX로 인해 스택에 삽입한 셸코드를 직접 실행하기 어려운 경우 사용하는 대표적인 공격 기법이다.
- 프로그램이나 라이브러리에 이미 존재하는 짧은 명령어 조각인 Gadget을 연결하여 원하는 동작을 수행하도록 만든다.
- 각 Gadget의 마지막에는 주로 `ret` 명령어가 존재하며, 이를 이용해 다음 Gadget으로 실행 흐름을 이어간다.

### 4-3. 공격 흐름 요약

```
입력 길이를 검사하지 않는 취약한 코드
             ↓
       버퍼 크기 초과 입력
             ↓
      인접한 스택 메모리 손상
             ↓
    반환 주소(RET) 덮어쓰기
             ↓
       함수 종료 및 ret 실행
             ↓
  공격자가 지정한 주소로 실행 흐름 이동
             ↓
   의도한 함수 실행 / 셸 획득 / FLAG 출력
```

※ 위는 반환 주소를 덮어쓰는 공격 시나리오를 단순화한 것으로, 실제 공격 성공 여부는 메모리 배치와 보호 기법에 따라 달라진다.

## 5. 완화 기법 (Mitigations)

현대 운영체제와 컴파일러는 스택 버퍼 오버플로우를 탐지하거나 공격을 어렵게 만드는 다양한 보호 기법을 제공한다.

| 보호 기법 | 주요 기능 | 익스플로잇에 미치는 영향 |
| --- | --- | --- |
| **Stack Canary** | 버퍼와 제어 데이터 사이에 특정 값을 저장하고, 함수 종료 시 값의 변조 여부를 검사 | Canary가 변경되면 비정상 종료시켜 반환 주소를 이용한 공격을 탐지할 수 있음 |
| **NX / DEP** | 스택 등의 메모리 영역에서 명령어 실행을 금지 | 스택에 삽입한 셸코드의 직접 실행을 방지하며, ROP 등 기존 실행 가능 코드를 이용한 공격이 대안으로 사용될 수 있음 |
| **ASLR** | 스택, 힙, 공유 라이브러리 등의 메모리 주소를 실행 시마다 무작위로 변경 | 공격자가 사용할 주소를 예측하기 어려워지며, 주소 정보 유출 등을 통한 우회가 시도될 수 있음 |
| **PIE** | 실행 파일의 코드 영역이 임의의 주소에 배치될 수 있도록 실행 파일을 생성 | 실행 파일 내부 함수 및 Gadget의 주소가 매 실행마다 달라질 수 있어 고정 주소를 이용한 공격이 어려워짐 |

**보호 기법별 핵심 정리**

- **Canary**: 스택 데이터가 변조되었는지 탐지한다.
- **NX / DEP**: 특정 메모리 영역에서 코드가 실행되는 것을 방지한다.
- **ASLR**: 메모리 주소를 무작위화한다.
- **PIE**: 실행 파일 자체의 코드 영역 주소를 무작위화할 수 있도록 지원한다.

※ 이러한 보호 기법은 공격을 어렵게 만드는 방어 계층이며, 버퍼 오버플로우 취약점 자체를 제거하는 것은 아니다. 여러 보호 기법을 함께 적용하는 것이 중요하다.

## 6. 방어 방법

1. **안전한 함수 및 문자열 처리 사용**
    - `gets()` 대신 버퍼 크기를 지정할 수 있는 `fgets()`를 사용한다.
    - `sprintf()` 대신 목적지 버퍼의 크기를 지정하는 `snprintf()`를 사용한다.
    - `strncpy()` 역시 널 종료 문자가 자동으로 보장되지 않는 경우가 있으므로, 복사 길이와 널 종료 처리를 함께 확인해야 한다.
2. **입력 길이 검증**
    - 입력 데이터가 버퍼의 크기를 초과하지 않도록 사전에 검사한다.
    - 문자열을 저장할 때는 널 종료 문자(`\0`)를 위한 공간까지 고려한다.
3. **컴파일러 및 운영체제 보호 기법 활성화**
    - Stack Canary, NX/DEP, ASLR, PIE 등의 보호 기법을 활성화한다.
    - GCC/Clang 등의 컴파일러에서 제공하는 보안 옵션을 활용한다.
4. **메모리 안전성 확보**
    - 가능하다면 Rust와 같은 메모리 안전 언어를 사용한다.
    - C/C++ 개발 시 정적 분석 도구와 AddressSanitizer(ASan) 등을 활용하여 메모리 오류를 탐지한다.

## 7. 핵심 정리

> 스택 버퍼 오버플로우는 스택에 할당된 버퍼에 크기를 초과하는 데이터를 기록하여 인접한 메모리 영역을 손상시키는 취약점이다.
> 
> 
> 공격자는 이를 이용해 반환 주소(RET) 등의 제어 데이터를 덮어쓰고, 함수 종료 시 실행 흐름을 원하는 위치로 변경할 수 있다.
> 
> 핵심은 **버퍼의 크기를 초과하는 데이터 입력 → 인접 메모리 손상 → 반환 주소 변조 → 실행 흐름 탈취**의 과정이며, 이를 방지하기 위해서는 안전한 메모리 처리와 입력 길이 검증, 컴파일러 및 운영체제의 보호 기법을 함께 적용해야 한다.
>
